# 出力層（classifier）のメモリ最適化方針

stories15M（llama2.c）の推論で最大の律速である出力層のメモリアクセスを最適化するための方針メモ。

## 0. 方針

**任意のマシンで、ベンチマークを回して最適な構成を決める。** 特定の CPU に合わせた値（コア番号、コアの種類ごとの帯域、L3 の容量、P/E の分担比など）はコードに書き込まず、そのマシンで測って決める。

これまで Intel Core Ultra 5 225U（以下「基準機」）に限定して計測と方針づくりをしてきた。基準機の結果（1〜5 節）は、何がマシンによって変わり、何がどのマシンでも効くかを見分けるための事例として残す。

改善は次の2つに分けて進める。

| 種類 | 内容 | 例 | 進め方 |
|---|---|---|---|
| **どのマシンでも効く改善** | 読む量や無駄な待ちを減らす。効果の大小はマシンで違っても、悪くなることはまずない | B 案（読む量の削減）、A1（huge page） | `run.c` に実装する。**次は B 案に取り掛かる**（第4節） |
| **マシンごとに最適値が変わる設定** | コアの選び方や分担のしかた | スレッド数と配置、P/E の分担比（A3）、E コアのプリフェッチ（A2）、`OMP_WAIT_POLICY`（A4 (a)） | ベンチマークで測って自動で選ぶ仕組みを作る（第6節。**後で着手**） |

最適な構成を自動で決める部分は、`プロジェクト/プロジェクトReatMe.md` の CPU-Profiler（CPU の構成を認識し、組み合わせを変えてベンチマークを回し、最適な構成で run する）と同じ目標なので、そちらと合わせて設計する。

## 1. 前提：何が律速か（基準機での計測）

### 1.1 forward の内訳

| ステージ | 1トークンで読む重み | parallel region/token | P1 (ms) | 割合 | P4_HT (ms) | 割合 |
|---|---|---|---|---|---|---|
| **final**（`wcls` 32000×288） | **36.9 MB** | 1 | 1.210 | **53%** | 0.760 | **46%** |
| ffn_up（w1, w3） | 10.6 MB | 12 | 0.371 | 16% | 0.309 | 19% |
| qkv（wq, wk, wv） | 6.0 MB | 18 | 0.243 | 11% | 0.253 | 15% |
| ffn_down（w2） | 5.3 MB | 6 | 0.217 | 9% | 0.154 | 9% |
| attention_output（wo） | 2.0 MB | 6 | 0.102 | 4% | 0.084 | 5% |
| compute_attention | （KV キャッシュ） | 6 | 0.111 | 5% | 0.079 | 5% |
| norm / RoPE / SwiGLU / embedding | ― | ―（直列） | 0.013 | <1% | 0.017 | 1% |
| **forward 合計** | **60.8 MB** | **49** | 2.292 | | 1.665 | |

- P1 = P コア1スレッド（CPU 0）、P4_HT = P コア2つ＋HT（CPU 0-3）
- 各ステージはトークンごとの中央値なので、足し合わせても forward 合計（forward の中央値）とは少しずれる
- matmul が forward の約 94% を占め、そのうち P1 で 56%、P4_HT で 49% が出力層
- 読み込んでいるのはトークンではなく**重み行列 `wcls`**。stories15M では埋め込み表と共有している（`memory_map_weights` の `shared_weights`）
- 1トークンで読む重みの量と、その中で出力層が占める割合（約 6 割）はモデルで決まり、マシンによらない。**出力層の読み込みを減らす B 案がどのマシンでも効くと考える根拠**

構成別の forward と出力層:

| 構成 | CPU | 層の合計 (ms) | 出力層 (ms) | forward (ms) | 出力層 GB/s | 平均周波数 |
|---|---|---|---|---|---|---|
| P1 | 0 | 1.065 | 1.210 | 2.292 | 30.5 | 4.79 GHz |
| P2 | 0,2 | 0.907 | 0.871 | 1.780 | 42.3 | 4.70 GHz |
| P4_HT | 0-3 | 0.900 | 0.760 | 1.665 | 48.5 | 4.59 GHz |
| **P4_HT + `OMP_WAIT_POLICY=active`** | 0-3 | **0.643** | 0.761 | **1.410** | 48.4 | 4.79 GHz |
| E4 | 4-7（1クラスタ） | 1.110 | 1.016 | 2.124 | 36.3 | 3.67 GHz |
| X4_2_2 | 4,5,8,9（2クラスタ） | 1.011 | 0.866 | 1.876 | 42.6 | 3.65 GHz |

- `OMP_WAIT_POLICY=active` の行だけ 2026-10-15 の計測（同じ日の既定の P4_HT は forward 1.698 ms）。`active` では層の部分だけが短くなり、**出力層が forward の 54% を占める**

### 1.2 律速の判断

**出力層はメモリ律速と見てよい。**

- 1トークンごとに 60.8MB の重みを読み直すが、L3 は 12MB しかないため、毎回 DRAM から読み込んでいる
- 計算量は 1 バイトあたり 0.5 FLOP しかない
- 出力層の帯域はスレッドを増やすと伸びる（P1 30.5 → P2 42.3 → P4_HT 48.5 GB/s）が、DRAM の理論帯域の約半分で頭打ちになっている

L3 の容量はマシンによって違うが、出力層だけで 36.9MB あるので、一般的なデスクトップ・ノート PC の CPU でもキャッシュには収まらず、メモリ律速になると考える。

**層の matmul には、帯域とは別に「呼び出し1回あたりの固定コスト」がある。**

P4_HT の各 matmul の時間は、`呼び出し回数 × 7.4 µs + 読むバイト数 ÷ 48.9 GB/s` で全ステージ 1% 以内に合う。

| ステージ | 呼び出し/token | 実測 (ms) | 当てはめ (ms) | 実効帯域 (GB/s) |
|---|---|---|---|---|
| final | 1 | 0.760 | 0.761 | 48.5 |
| ffn_up | 12 | 0.309 | 0.306 | 34.4 |
| ffn_down | 6 | 0.154 | 0.153 | 34.5 |
| qkv | 18 | 0.253 | 0.255 | 23.6 |
| wo | 6 | 0.084 | 0.085 | 23.7 |

- P4_HT の forward 1.665 ms のうち、**約 0.32 ms（19%）は 43 回の matmul 呼び出しの固定コスト**
- 小さい matmul ほど実効帯域が低いのはこのため。qkv は P1（0.243 ms）より P4_HT（0.253 ms）の方が遅く、スレッドを増やしても全く伸びない
- 初版では「処理時間が重みのバイト数にほぼ比例する」ことをメモリ律速の根拠にしていたが、今回の計測では比例しない（qkv/wo の時間比は P1 で 2.4、重みの比は 3.0）。その差はこの固定コストで説明できる

**固定コストの正体は OpenMP の待ち方。** 単体ベンチマークで同じ行列を K 回の並列区間に分けて読み、K に対する時間の傾きを測った。

| P4_HT | 並列区間だけ (µs/回) | fp32 matmul (µs/回) |
|---|---|---|
| `OMP_WAIT_POLICY` 既定 | 5.62 | **7.63**（上の当てはめの 7.4 µs とほぼ一致） |
| `OMP_WAIT_POLICY=active` | 0.49 | 1.54 |

- 既定の待ち方では、並列区間と並列区間の間で待機スレッドが休眠し、次の区間で起こし直すコストがかかる。`active` にすると待機スレッドが休眠せずに待つので、ほぼ消える
- `run_baseline.sh` で確認した結果、P4_HT の forward は 1.698 → 1.410 ms（−17%）、計測コードなしの tok/s は 579 → 702（+21%）。層の部分が 0.29 ms 短くなり、上の見積もり（約 0.25 ms）と合う
- P1 は 1 スレッドなので関係ない。待ち時間の長さや起こし直しのコストは OS・OpenMP の実装・コア数で変わるので、**既定と `active` のどちらがよいかはマシンごとに測って決める**（第6節）

**HT の効果は小さい。** P2 → P4_HT で forward は 1.07 倍、出力層は 1.15 倍、層の合計は 1.01 倍にとどまる。

### 1.3 初版の数値との違い

| | 初版 P1 | 今回 P1 | 初版 P4_HT | 今回 P4_HT |
|---|---|---|---|---|
| final (ms) | 2.627 | 1.210 | 0.793 | 0.760 |
| forward (ms) | 4.832 | 2.292 | 1.628 | 1.665 |

- **P1 が約2倍速くなった**。初版はステージごとに stderr へ `fprintf` していた（stderr はバッファされないので1行ごとにシステムコールが入る）。計測時の電源状態も記録がないため、どちらが主因かは切り分けられない。P4_HT はほぼ同じ
- 関数とループの配置を 64 バイトに揃えないと、`run.c` を少し変えるだけで P1 の速さが約 10% 変わる（機械語は同じで配置だけが違うビルドで確認）。今回の計測は配置を揃えている

## 2. マシンによって変わる量

### 2.1 基準機の特性

| 項目 | 値 |
|---|---|
| CPU | Intel Core Ultra 5 225U（P コア2つ（HT 付き）、E コア8つ、LP-E コア2つ、14 スレッド） |
| L2 | P コアごとに 2MiB（CPU 0-1、2-3 で共有）、E コアは 4コアのクラスタごとに 2MiB を共有（cluster_a = CPU 4-7、cluster_b = CPU 8-11） |
| L3 | 12MB（CPU 0-11 で共有。LP-E コアの CPU 12, 13 は共有しない） |
| DRAM | DDR5-5600 × 2ch、理論帯域 **89.6 GB/s** |
| SIMD 命令 | AVX2, FMA, F16C, AVX-VNNI（AVX-512 なし） |
| 出力層の実効帯域（`run.c` の中） | P1 30.5 GB/s、P2 42.3 GB/s、P4_HT 48.5 GB/s（理論値の約 54%）、E4（1クラスタ）36.3 GB/s、X4_2_2（2クラスタ）42.6 GB/s |
| 読み込みの上限（単体、読むだけ） | P1 28.5 GB/s、P4_HT 57.7 GB/s、X4_2_2 53.3 GB/s、P4X（P4_HT + X4_2_2）83.8 GB/s（理論値の 94%） |
| L3 に収まる目安 | 10MB 未満。8MB までは繰り返し読むと約 115 GB/s、10MB で下がり始め、12MB 以上で大きく下がる。他の重みで追い出される状況では約 50 GB/s |
| 周波数・電力（AC 電源） | P コアは P4_HT でも 4.8 GHz（Bzy_MHz）を維持、パッケージ電力 約 25W。E コアは 3.8 GHz、約 18W |

基準機では、P コアだけでは DRAM 帯域を使い切れず（P4_HT の上限 57.7 GB/s）、E コアを足すと理論値に近づく（P4X で 83.8 GB/s）。

### 2.2 マシンごとに測る・調べる項目

最適な構成を自動で決める仕組み（第6節）で扱う項目。基準機で効き方が分かったものを挙げる。

| 項目 | 調べ方 | 影響する案 |
|---|---|---|
| コアの種類と並び（P/E、HT の相方、L2/L3 を共有する範囲） | sysfs（`/sys/devices/cpu_core/cpus`、`cpu_atom/cpus`、`cache/index*/shared_cpu_list`）。`bench_memopt/env/` と同じ情報 | スレッド数と配置、A3 |
| 使える SIMD 命令（AVX2、F16C、AVX-VNNI、AVX-512、AVX-512 VNNI、ARM なら NEON / dotprod） | `cpuid`（`__builtin_cpu_supports`）や `/proc/cpuinfo` | B 案のカーネルの選択（第4節） |
| コアの組み合わせごとの読み込み帯域 | `bench_cls --kernel read` | スレッド数と配置、A3 の分担比 |
| L3 に実際に収まる量 | `bench_cls` のデータ量スイープ | 第5節 |
| 並列区間 1 回のコスト（既定と `active`） | `bench_cls --kernel none --split K` | A4 (a) |
| huge page が使えるか | `/sys/kernel/mm/transparent_hugepage/enabled` | A1 |

**DRAM 帯域を使い切れていないマシンでは「読み方の改善（A）」、使い切っているマシンでは「読む量の削減（B）」が効く。** B はどちらの場合も読む量そのものを減らすので、どのマシンでも効く。

## 3. A. 読み込み方の改善（ロスレス）

どの案も出力が変わらないので、stdout の sha256 が一致するかで正しさを確認できる。

| 案 | 内容 | マシンへの依存 |
|---|---|---|
| A1. huge page | 重みを `mmap` から匿名メモリにコピーし、`madvise(MADV_HUGEPAGE)` で 2MB ページに載せる | 小さい。Linux で THP が使えれば基本的に効く。使えない環境では今のまま |
| A2. 複数行を同時に処理 / ソフトウェアプリフェッチ | `matmul` の内側で 4 行を同時に計算する／先読み命令を入れる | **大きい**。基準機では P コアには効かず、E コアにだけ効いた。コアの種類ごとに有効・無効を決める |
| A3. 出力層だけ複数種類のコアで分担 | 出力層の行を P コアと E コアに配る（均等、または帯域比で重み付け） | **大きい**。ハイブリッド CPU だけが対象。分担比はコアの組み合わせごとの帯域から決める |
| A4. 呼び出しごとの固定コストを減らす | (a) `OMP_WAIT_POLICY=active` で待機スレッドを休眠させない。(b) wq/wk/wv の3つ、w1/w3 の2つを1つの並列区間で計算する | (a) は OS・OpenMP の実装・コア数で効き方が変わり、消費電力も増えるので測って決める。(b) はどのマシンでも呼び出し回数が減るが、(a) の後なら効果は小さい |

### 3.1 基準機での単体ベンチマークの結果

出力層 1 回の時間。P4X = P4_HT + X4_2_2 の 8 スレッド（CPU 0-3, 4, 5, 8, 9）。

| 条件 | P4_HT | X4_2_2 | P4X |
|---|---|---|---|
| **現状**（fp32、mmap のまま） | **726 µs** | 794 µs | 504 µs |
| fp32、4KB ページにコピー（A1 の比較用） | 700 | 812 | 515 |
| A1（2MB ページにコピー） | 665 | 792 | 500 |
| A2（4 行同時、2MB） | 654 | 786 | 501 |
| A2 + プリフェッチ 2KB（2MB） | 646 | **659** | **451** |
| 上限の目安（読むだけ、2MB） | 639 | 692 | 440 |

| 案 | 結果 |
|---|---|
| A1 | P4_HT で −8%（726 → 665 µs）。うちコピー（4KB）で −3.5%、2MB ページで −5%。コピーで各行の先頭が 64 バイト境界に揃う影響も含む |
| A2 | 4 行同時は P4_HT で −2%。プリフェッチは P コアでは効果なし（P1 では 6% 遅くなる）、**E コアで大きい**（X4_2_2 で −16%、P4X で −10%）。プリフェッチの距離は 2KB しか試していない |
| A3 | P4X は均等分割でも P4_HT より 25% 速い（2MB で 665 → 500 µs）。4 行同時 + プリフェッチで 451 µs、現状から −38%。帯域比の重み付けは fp32 で 2〜3.5% |
| A4 (a) | `run.c` の P4_HT で forward −17%（1.2 節） |
| A4 (b) | (a) の後の残りは約 1.5 µs/回 × 43 回 ≈ 0.07 ms |

A3 の注意点：

- E コアは1クラスタに詰めるより、クラスタにまたがって配置する方が速かった（E4 36.3 GB/s、X4_2_2 42.6 GB/s）。初版の計測では P2E2（CPU 0,2,4,5）が P1 より遅かった。配置の良し悪しはマシンで変わるので、候補を測って選ぶ
- 出力層以外の層まで E コアに広げると、小さい matmul では同期の待ちが増えるので、まずは出力層だけにする

## 4. B. 読む量の削減（次に実装する）

出力層の重みを小さい形式で持ち、読む量を減らす。読む量がそのまま時間になるので、**どのマシンでも効く**。

### 4.1 案と基準機での見積もり

見積もりは基準機の P4_HT の出力層の実効帯域 48.5 GB/s を使い、層の部分（0.90 ms）は変わらないとした。単体ベンチマークの値は P4_HT、2MB ページ。

| 案 | 出力層の重み | 出力層の時間（見積もり） | 単体ベンチマーク | forward | 出力への影響 |
|---|---|---|---|---|---|
| 現状 fp32 | 36.9 MB | 0.76 ms | 665 µs | 1.67 ms | ― |
| B1. fp16 / bf16 | 18.4 MB | 約 0.38 ms | 367 µs | 約 1.29 ms（1.3×） | ほぼ無し。単体での最大誤差 3×10⁻⁴ |
| B2. int8（32要素ごとにスケール） | 約 10.4 MB | 約 0.21 ms | 161 µs | 約 1.12 ms（1.5×） | 少しあり。単体での最大誤差 0.013、argmax は一致 |
| B3. int4 | 約 5.2 MB | 約 0.11 ms | 未計測 | 約 1.01 ms（1.6×） | あり |
| **B4. 2段階の厳密な argmax** | 約 10.4 MB + 少数の行 | 約 0.21 ms | 未計測（int8 部分は B2 と同じ） | 約 1.12 ms（1.5×） | **greedy（`-t 0`）なら出力は完全に同じ** |
| B5. 語彙の絞り込み | 使う語彙の割合に比例 | 割合次第 | 未計測 | ― | 学習データに出てこないトークンは生成されなくなる |

- 単体ベンチマークでは読む量にほぼ比例して速くなった（fp16 で 0.55 倍、int8 で 0.24 倍）。ただし単体ベンチマークは同じ行列を繰り返し読むので、10.4MB や 18.4MB の重みの一部が L3 に残り、速めに出る。`run.c` では他の層の重みで追い出されるので、見積もり（48.5 GB/s で割った値）の方が近いと考える
- `OMP_WAIT_POLICY=active`（層の部分 0.64 ms）と組み合わせると、B2/B4 で forward は約 0.86 ms（基準機 P4_HT で現状 1.67 ms の約 2 倍速）になる見込み
- 出力層を削るほど、層の部分の比率が上がる。B2/B4 の後は forward の約 7〜8 割が層の部分になるので、その先は層の重みの量子化（第5節）が効く

### 4.2 実装の順番

1. **B2 の int8 カーネルを `run.c` に入れる**：B4 の1段目でもあるので先に作る。単体ベンチマークの `k_int8`（`bench_memopt/bench_cls.c`）を元にする
2. **B4（2段階の厳密な argmax）**：B2 のカーネルに、誤差の上限による候補の絞り込みと、候補だけの fp32 再計算を足す。greedy なら出力が変わらないので、sha256 で正しさを確認できる
3. **B1（fp16）**：B4 が使えない場合（`-t 0` 以外のサンプリング）に、誤差の小さい選択肢として
4. B3（int4）、B5（語彙の絞り込み）は、第5節（キャッシュに収める）とあわせて検討する

### 4.3 どのマシンでも動かすための注意

- **SIMD 命令ごとにカーネルを用意し、実行時に選ぶ**。基準機では int8 の内積に AVX-VNNI（`vpdpbusd`）を使ったが、持っていないマシンも多い。最低限、次の3段を用意する
  - 移植用のスカラー版（どのマシンでも動く。正しさの基準にもする）
  - AVX2 版（`maddubs` + `madd`。x86-64 の多くのマシンで使える）
  - AVX-VNNI / AVX-512 VNNI 版（使えるマシンだけ）
  - ARM で動かす場合は NEON（`sdot`）版を追加する
- `-march=native` でビルドすると、ビルドしたマシンの命令しか使えない（他のマシンに持っていくと落ちる）。`__builtin_cpu_supports` と関数の属性（`__attribute__((target("avx2")))` など）で、1つのバイナリの中で切り替える方式を基本にする
- fp16 の変換は x86 では F16C 命令が必要。無いマシンではスカラーで変換する（B1 は、変換が遅いと読む量の削減の効果が打ち消される可能性がある）
- 出力層用の量子化したコピーは、モデルを読み込むときに作る（読み込みが少し遅くなる）。埋め込み表として使う fp32 の元データは残す（埋め込み表は1トークンにつき1行しか読まないので、速度に影響しない）
- `runq.c` は全重みを int8（Q8_0）に量子化する既存の実装なので、B2 の簡易的な比較対象として使える

### 4.4 正しさの確認

- **B4**：`-t 0` で stdout の sha256 が master と一致すること（今の `golden.sha256` と同じ確認）。あわせて、候補として残った行数（平均・最大）を記録し、2段目の再計算のコストを把握する
- **B1 / B2**：出力が変わるので sha256 では確認できない。次の指標で評価する
  - 出力層の値の誤差（fp32 との最大誤差・平均誤差）
  - greedy で生成したトークン列が fp32 と何トークン目まで一致するか（複数のプロンプトで）
  - 必要なら、検証用データでの perplexity（`train.py` の評価と同じ方法）

### 4.5 B4. 2段階の厳密な argmax

1. int8 の近似値で、32000 語すべてのスコアを計算する
2. 量子化の誤差には上限があるので、各行の「真の値の範囲」（上限と下限）がわかる
3. 上限が、近似値の1位の下限以上になる行だけを候補として残す
4. 候補の行だけを fp32 で計算し直し、argmax を取る

greedy の結果は量子化しない場合と完全に一致する。top-p サンプリングにも応用できるが、その場合は確率の誤差を別途見積もる必要がある。

誤差の上限は、32 要素のグループごとに「重みの量子化誤差（スケールの半分以下）× x の絶対値の和」と「x の量子化誤差」の分を足して求める。上限がゆるすぎると候補が増えて2段目が重くなるので、実装後に候補の数を見て調整する。

### 4.6 B5. 語彙の絞り込み

TinyStories は簡単な英語の物語なので、Llama 2 の語彙 32000 のうち実際に使われるのは一部だけのはず。どれくらい絞れるかは、`tinystories.py pretokenize` で学習データを処理し、トークン頻度を数えて決める。

## 5. 1トークンで読むデータをキャッシュに収める

1トークンあたりに読むデータ全体が L3 に収まれば、2トークン目以降はほとんど DRAM を読まずに済む。基準機の単体ベンチマークでは、L3 に収まると帯域は約 2.3 倍（約 115 GB/s 対 約 50 GB/s）になった。

| 構成 | 1トークンで読むデータ量 |
|---|---|
| 現状（層の重み 23.9 + 出力層 36.9 + KV キャッシュ 最大3.5） | 約 64 MB |
| 層の重みを int8（約6.8）+ 出力層を int4（約5.2）+ KV キャッシュを fp16（1.8） | 約 13.8 MB |
| 上の構成 + 語彙の絞り込み（B5） | 語彙の割合に応じて減る |

- **収まるかどうかは L3 の容量で決まるので、マシンごとに違う**。目標のデータ量は、そのマシンでデータ量スイープを回して決める（基準機では 12MB の L3 に対して 10MB 未満。上の 13.8MB の構成では収まらず、出力層（int4）を約 1.4MB 以下、つまり語彙を 3 割程度まで絞る必要がある）
- L3 の大きいマシン（数十 MB 以上）では、量子化だけで収まる可能性がある
- 基準機では LP-E コア（CPU 12, 13）は L3 を共有していない。L3 を共有するコアの範囲もマシンごとに調べる
- KV キャッシュの読み込み量は、生成が進むほど（`pos` が大きくなるほど）増える
- L3 に収まって帯域の制約が外れると、1.2 節の呼び出しごとの固定コストがそのまま残る。A4（特に `OMP_WAIT_POLICY`）と組み合わせて考える

## 6. 最適な構成を自動で決める（後で着手）

任意のマシンで、ベンチマークを回して次の設定を決め、以後の run でその設定を使う仕組み。CPU-Profiler（`プロジェクト/プロジェクトReatMe.md`）と同じ目標なので、合わせて設計する。

| 決める設定 | 候補の作り方 | 測り方 |
|---|---|---|
| 層の matmul のスレッド数と配置 | コアの種類と L2/L3 を共有する範囲から、HT の有無、クラスタのまたぎ方を組み合わせる | `run.c` の forward（`run_baseline.sh` と同じ方法） |
| 出力層のスレッド数・配置・分担比（A3） | 上と同様。分担比はコアの組み合わせごとの読み込み帯域から決める | 出力層の単体ベンチマークと forward |
| プリフェッチの有無と距離（A2） | コアの種類ごとに | 出力層の単体ベンチマーク |
| `OMP_WAIT_POLICY`（A4 (a)） | 既定 / `active` | forward |
| B 案のカーネル | 使える SIMD 命令から | 単体ベンチマーク（正しさの確認を含む） |

- 組み合わせが多いので、基準機で効いたもの・効かなかったものを手がかりに候補を絞る（例：P コアのみ、P コア + E コアの各クラスタから半分ずつ、など）
- 計測時間を短くするため、出力層は単体ベンチマークで、全体は少ないトークン数の forward で測る
- 決めた設定の保存方法と、run がそれを読む方法（設定ファイル、環境変数、Makefile のターゲットなど）は、着手時に決める

## 8. 計測についての注意

- **ステージごとの計測は `-DSTAGE_TIMING` で行う**。forward の中では配列に記録するだけで、出力は生成が終わってからまとめて行う。計測コードの影響は tok/s で P1 +0.2%、P4_HT +0.3〜0.5%
- **周波数と電力を記録する**。`perf stat` の cycles ÷ task-clock と、turbostat の Bzy_MHz / PkgWatt / PkgTmp。ハイブリッド CPU では cycles が `cpu_core` と `cpu_atom` に分かれて出る
- **トポロジーを結果と一緒に保存する**。`bench_memopt/env/` を毎回の結果フォルダにコピーしている。基準機では `lscpu -e` の L2 欄が CPU 8, 10 で壊れて表示されたので、sysfs から取る（`cache_sharing.txt`）
- **関数とループの配置を 64 バイトに揃えてビルドする**。揃えないと、機械語が同じでも配置の違いだけで P1 の速さが約 10% 変わった。最適化案の効果を比べるビルドはすべて `-falign-functions=64 -falign-loops=64` を付ける
- **AC 電源につなぎ、電源設定を性能優先にする**（Linux なら EPP を performance）。基準機ではバッテリー駆動でスレッドを増やしたときに周波数が下がった
- **ブラウザなどを閉じて計測する**。基準機の Step 2 の 1 回目はブラウザを開いたまま計測し、ばらつきが 10% を超える条件が 11 個出た。閉じて再計測すると 7 個に減った（`プロジェクト/progress-2026-10-15.md` 3.6 節）
- **他のプロセスの負荷に注意する**。HT の相方を空けた構成（基準機の P2 など）は、そこで別のプロセスが動くとコアの資源を直接取り合う。基準機の計測では、遅い回ほど計測に使っていない CPU の Busy% が高かった
- **単体ベンチマークの値の偏りに注意する**。基準機では P1 の値が `run.c` の中より遅く出た（mmap のままの fp32 で 1.65 ms 対 1.25 ms、原因未解明）。P4_HT は整合している（726 µs 対 760 µs）。また、同じ行列を繰り返し読むので、L3 に収まる程度以下のデータは速めに出る
- huge page の扱いは OS によって違う。今の計測スクリプトは Linux 用（sysfs、`perf`、`turbostat`、`taskset`）。他の OS で回す場合は、トポロジーの取得と CPU の割り当ての方法を別に用意する
