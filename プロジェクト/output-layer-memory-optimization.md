# 出力層（classifier）のメモリ最適化方針

対象マシン（Intel Core Ultra 5 225U）に限定して、stories15M 推論の最大の律速である出力層のメモリアクセスを最適化するための方針メモ。

- 計測データの出典: `bench_memopt/baseline/20261013_163724/`（2026-10-13 計測、Linux、AC 電源・EPP performance、`gcc -Ofast -fopenmp -march=native -falign-functions=64 -falign-loops=64`、ログを出さない計測モード `-DSTAGE_TIMING`、`-n 256 -t 0 -s 42 -i "Once upon a time"`、5回の中央値、先頭16トークンを除く）。計測方法は `bench_memopt/README.md`
- 出力層の単体ベンチマーク（Step 2）の出典: `bench_memopt/cls/20261015_134803/`（2026-10-15 計測、同じ環境・ビルド、`bench_memopt/bench_cls.c`、各条件 0.5 秒以上の中央値を 3 回繰り返した中央値）。詳しい結果とばらつきの注記は `プロジェクト/progress-2026-10-15.md`
- 初版の数値は `dev/wataru` ブランチの `benchmark_affinity_stories15M/`（2026-10-12 計測）だった。違いは 1.3 節
- 見積もりはすべて「処理時間は読み込む重みのバイト数に比例する」という仮定（と 1.2 節の固定コスト）に基づく概算であり、実測で確認が必要

## 1. 前提：何が律速か

### 1.1 forward の内訳

| ステージ | 1トークンで読む重み | parallel region/token | P1 (ms) | 割合 | P4_HT (ms) | 割合 |
|---|---|---|---|---|---|---|
| **final**（`wcls` 32000×288） | **36.9 MB** | 1 | 1.210 | **53%** | 0.760 | **46%** |
| ffn_up（w1, w3） | 10.6 MB | 12 | 0.371 | 16% | 0.309 | 19% |
| qkv（wq, wk, wv） | 6.0 MB | 18 | 0.243 | 11% | 0.253 | 15% |
| ffn_down（w2） | 5.3 MB | 6 | 0.217 | 9% | 0.154 | 9% |
| attention_output（wo） | 2.0 MB | 6 | 0.102 | 4% | 0.084 | 5% |
| compute_attention | （KV キャッシュ） | 6 | 0.111 | 5% | 0.079 | 5% |
| norm / RoPE / SwiGLU / embedding | ― | ―（直列） | 0.013 | <1% | 0.017 | 1% |
| **forward 合計** | **60.8 MB** | **49** | 2.292 | | 1.665 | |

- P1 = P コア1スレッド（CPU 0）、P4_HT = P コア2つ＋HT（CPU 0-3、現時点の最速構成）
- 各ステージはトークンごとの中央値なので、足し合わせても forward 合計（forward の中央値）とは少しずれる
- matmul が forward の約 94% を占め、そのうち P1 で 56%、P4_HT で 49% が出力層
- 読み込んでいるのはトークンではなく**重み行列 `wcls`**。stories15M では埋め込み表と共有している（`memory_map_weights` の `shared_weights`）

構成別の forward と出力層:

| 構成 | CPU | 層の合計 (ms) | 出力層 (ms) | forward (ms) | 出力層 GB/s | 平均周波数 |
|---|---|---|---|---|---|---|
| P1 | 0 | 1.065 | 1.210 | 2.292 | 30.5 | 4.79 GHz |
| P2 | 0,2 | 0.907 | 0.871 | 1.780 | 42.3 | 4.70 GHz |
| **P4_HT** | 0-3 | 0.900 | **0.760** | **1.665** | **48.5** | 4.59 GHz |
| E4 | 4-7（1クラスタ） | 1.110 | 1.016 | 2.124 | 36.3 | 3.67 GHz |
| X4_2_2 | 4,5,8,9（2クラスタ） | 1.011 | 0.866 | 1.876 | 42.6 | 3.65 GHz |

### 1.2 律速の判断

**出力層はメモリ律速と見てよい。**

- 1トークンごとに 60.8MB の重みを読み直すが、L3 は 12MB しかないため、毎回 DRAM から読み込んでいる
- 計算量は 1 バイトあたり 0.5 FLOP しかない
- 出力層の帯域はスレッドを増やすと伸びる（P1 30.5 → P2 42.3 → P4_HT 48.5 GB/s）が、DRAM の理論帯域の約半分で頭打ちになっている

**層の matmul には、帯域とは別に「呼び出し1回あたりの固定コスト」がある。**

P4_HT の各 matmul の時間は、`呼び出し回数 × 7.4 µs + 読むバイト数 ÷ 48.9 GB/s` で全ステージ 1% 以内に合う。

| ステージ | 呼び出し/token | 実測 (ms) | 当てはめ (ms) | 実効帯域 (GB/s) |
|---|---|---|---|---|
| final | 1 | 0.760 | 0.761 | 48.5 |
| ffn_up | 12 | 0.309 | 0.306 | 34.4 |
| ffn_down | 6 | 0.154 | 0.153 | 34.5 |
| qkv | 18 | 0.253 | 0.255 | 23.6 |
| wo | 6 | 0.084 | 0.085 | 23.7 |

- つまり P4_HT の forward 1.665 ms のうち、**約 0.32 ms（19%）は 43 回の matmul 呼び出しの固定コスト**。正体は OpenMP の待機スレッドの起こし直し（下記）
- 小さい matmul ほど実効帯域が低いのはこのため。qkv は P1（0.243 ms）より P4_HT（0.253 ms）の方が遅く、スレッドを増やしても全く伸びない
- P1 でも同じ形の式で ±20% 程度に合う（約 3 µs/回、30.5 GB/s）。1スレッドなので同期のコストは小さい
- 初版では「処理時間が重みのバイト数にほぼ比例する」ことをメモリ律速の根拠にしていたが、今回の計測では比例しない（qkv/wo の時間比は P1 で 2.4、重みの比は 3.0）。その差はこの固定コストで説明できる

**固定コストの正体は OpenMP の待ち方（Step 2 で確認）。** 単体ベンチマークで同じ行列を K 回の並列区間に分けて読み、K に対する時間の傾きを測った。

| P4_HT | 並列区間だけ (µs/回) | fp32 matmul (µs/回) |
|---|---|---|
| `OMP_WAIT_POLICY` 既定 | 5.62 | **7.63**（上の当てはめの 7.4 µs とほぼ一致） |
| `OMP_WAIT_POLICY=active` | 0.49 | 1.54 |

- 既定の待ち方では、並列区間と並列区間の間で待機スレッドが休眠し、次の区間で起こし直すコストがかかる。`active` にすると待機スレッドが休眠せずに待つので、ほぼ消える
- `run.c` を変えずに `OMP_WAIT_POLICY=active` を付けるだけで、P4_HT が 628 → 709 tok/s（+13%）になった（既定と交互に 3 回ずつの簡易確認。`run_baseline.sh` での計測はまだ）
- P1 は 1 スレッドなので、もともと 0.14 µs/回で関係ない

**HT の効果は小さい。** P2 → P4_HT で forward は 1.07 倍、出力層は 1.15 倍、層の合計は 1.01 倍にとどまる。初版では 1.45 倍で、HT が効くことをメモリ律速の根拠の一つにしていたが、今回の計測では成り立たない。

### 1.3 初版の数値との違い

| | 初版 P1 | 今回 P1 | 初版 P4_HT | 今回 P4_HT |
|---|---|---|---|---|
| final (ms) | 2.627 | 1.210 | 0.793 | 0.760 |
| forward (ms) | 4.832 | 2.292 | 1.628 | 1.665 |

- **P1 が約2倍速くなった**。初版はステージごとに stderr へ `fprintf` していた（stderr はバッファされないので1行ごとにシステムコールが入る）。計測時の電源状態も記録がないため、どちらが主因かは切り分けられない。P4_HT はほぼ同じ
- 関数とループの配置を 64 バイトに揃えないと、`run.c` を少し変えるだけで P1 の速さが約 10% 変わる（機械語は同じで配置だけが違うビルドで確認）。今回の計測は配置を揃えている
- 初版の P1 の値（P コア1つで 14 GB/s）から立てた見込みは、本版で書き直した

## 2. 対象マシンの特性

| 項目 | 値 |
|---|---|
| CPU | Intel Core Ultra 5 225U（P コア2つ（HT 付き）、E コア8つ、LP-E コア2つ、14 スレッド） |
| L2 | P コアごとに 2MiB（CPU 0-1、2-3 で共有）、E コアは 4コアのクラスタごとに 2MiB を共有（cluster_a = CPU 4-7、cluster_b = CPU 8-11） |
| L3 | 12MB（CPU 0-11 で共有。LP-E コアの CPU 12, 13 は共有しない） |
| DRAM | DDR5-5600 × 2ch、理論帯域 **89.6 GB/s** |
| SIMD 命令 | AVX2, FMA, F16C, AVX-VNNI（AVX-512 なし） |
| 出力層の実効帯域（`run.c` の中） | P1 30.5 GB/s、P2 42.3 GB/s、P4_HT 48.5 GB/s（理論値の約 54%）、E4（1クラスタ）36.3 GB/s、X4_2_2（2クラスタ）42.6 GB/s |
| 読み込みの上限（単体、読むだけ） | P1 28.5 GB/s、P4_HT 57.7 GB/s、X4_2_2 53.3 GB/s、**P4X（P4_HT + X4_2_2）83.8 GB/s（理論値の 94%）** |
| L3 に収まる目安 | **10MB 未満**。8MB までは繰り返し読むと約 115 GB/s、10MB で下がり始め、12MB 以上で大きく下がる。他の重みで追い出される状況では約 50 GB/s |
| 周波数・電力（AC 電源） | P コアは P4_HT でも 4.8 GHz（Bzy_MHz）を維持、パッケージ電力 約 25W。E コアは 3.8 GHz、約 18W |

**DRAM 帯域は P コアだけでは使い切れない。** P4_HT 単独では、単純に読むだけでも 57.7 GB/s で頭打ちになり、現状の出力層（単体で 50.8 GB/s）はその 88% まで出ている。理論値に近づけるには E コアの帯域を足す必要がある（P4X で 83.8 GB/s）。また、層の matmul では呼び出しごとの固定コストが無視できない（1.2 節）。そこで改善の方向は次の2つ。

- **A. 読み込み方を改善する**：同じバイト数を、より高い帯域・より少ない固定コストで読む
- **B. 読む量を減らす**：バイト数そのものを削る

## 3. A. 読み込み方の改善（ロスレス）

どの案も出力が変わらないので、stdout の sha256 が一致するかで正しさを確認できる。

| 案 | 内容 | 期待した理由 |
|---|---|---|
| A1. huge page | 重みを `mmap` から匿名メモリにコピーし、`madvise(MADV_HUGEPAGE)` で 2MB ページに載せる | 今は 4KB ページで、36.9MB は約 9000 ページになる。ハードウェアのプリフェッチャーは 4KB 境界を越えないので、境界ごとに先読みが途切れている。TLB ミスも減る。THP は `madvise` モードなのでそのまま使える |
| A2. 複数行を同時に処理 | `matmul` の内側で 4〜8 行を同時に計算する／ソフトウェアプリフェッチを入れる | 1コアあたりの同時メモリ要求数が増える |
| A3. 出力層だけ P+E で分担 | 出力層の行を P コアと E コアに配る（均等、または帯域比 P4_HT 約48 : X4_2_2 約43 で重み付け） | 出力層は行数が多いので同期コストが小さく、E コアの帯域を足し込める |
| A4. 呼び出しごとの固定コストを減らす（Step 1 の計測から追加） | (a) `OMP_WAIT_POLICY=active` で待機スレッドを休眠させない。(b) wq/wk/wv の3つ、w1/w3 の2つを1つの並列区間で計算する。さらに forward 全体を1つの `omp parallel` に入れる | P4_HT では matmul 1回あたり約 7.4 µs の固定コストがあり、forward の約 19%（0.32 ms）を占める |

### 3.1 単体ベンチマークの結果（Step 2）

出力層 1 回の時間。P4X = P4_HT + X4_2_2 の 8 スレッド（CPU 0-3, 4, 5, 8, 9）。

| 条件 | P4_HT | X4_2_2 | P4X |
|---|---|---|---|
| **現状**（fp32、mmap のまま） | **726 µs** | 794 µs | 504 µs |
| fp32、4KB ページにコピー（A1 の比較用） | 700 | 812 | 515 |
| A1（2MB ページにコピー） | 665 | 792 | 500 |
| A2（4 行同時、2MB） | 654 | 786 | 501 |
| A2 + プリフェッチ 2KB（2MB） | 646 | **659** | **451** |
| 上限の目安（読むだけ、2MB） | 639 | 692 | 440 |

| 案 | 結果 | 判断 |
|---|---|---|
| A1 | P4_HT で −8%（726 → 665 µs）。うちコピー（4KB）で −3.5%、2MB ページで −5%。コピーで各行の先頭が 64 バイト境界に揃う影響も含む | 実装が簡単なので入れる。出力層の重みのコピー（36.9MB）分メモリが増える |
| A2 | 4 行同時は P4_HT で −2%。プリフェッチは P コアでは効果なし、**E コアで大きい**（X4_2_2 で −16%、P4X で −10%） | P コア単独では見送り。A3 と組み合わせて E コアに使う。プリフェッチ距離は 2KB しか試していない |
| A3 | P4X は均等分割でも P4_HT より 25% 速い（2MB で 665 → 500 µs）。**4 行同時 + プリフェッチで 451 µs、現状から −38%**、実効帯域 81.8 GB/s は上限（83.8 GB/s）にほぼ届く。帯域比の重み付けは fp32 で 2〜3.5% | 効果が最大。出力層だけ P4X で分担し、E コアにプリフェッチを入れる |
| A4 (a) | fp32 matmul の固定コストが 7.63 → 1.54 µs/回。`run.c` の P4_HT で +13%（簡易確認） | **最優先**。コード変更なしで入る |
| A4 (b) | (a) の後の残りは約 1.5 µs/回 × 43 回 ≈ 0.07 ms | (a) の後なら効果は小さい。後回し |

A3 の注意点：

- 初版の計測では P2E2（CPU 0,2,4,5）が P1 より遅かった。E コアは1クラスタに詰めるより、クラスタにまたがって配置する方が速い（E4 36.3 GB/s、X4_2_2 42.6 GB/s）
- 単体ベンチマークの P4X の平均周波数は 4.69 GHz で、E コア（3.8 GHz）を含めた平均としては高く、P コアは 4.8 GHz 付近を維持していると見られる。ただし turbostat は記録していないので、`run.c` に入れたときに確認する
- 出力層以外の層まで E コアに広げると、小さい matmul では同期の待ちが増えるので、まずは出力層だけにする

A4 (a) の注意点：

- `active` では待機スレッドが休眠せずに CPU を使い続けるので、消費電力が増える。バッテリー駆動では周波数の低下と合わせて評価する
- P4X で使う場合は E コアのスレッドも待ち続ける。出力層だけを P4X にする場合のスレッドの持ち方（OpenMP のスレッド数を区間ごとに変えるか、常に 8 スレッドにするか）は実装時に決める

## 4. B. 読む量の削減

見積もりは P4_HT の出力層の実効帯域 48.5 GB/s を使い、層の部分（0.90 ms）は変わらないとした。単体ベンチマークの値は P4_HT、2MB ページ。

| 案 | 出力層の重み | 出力層の時間（見積もり） | 単体ベンチマーク | forward | 精度への影響 |
|---|---|---|---|---|---|
| 現状 fp32 | 36.9 MB | 0.76 ms | 665 µs | 1.67 ms | ― |
| B1. fp16 / bf16 | 18.4 MB | 約 0.38 ms | 367 µs | 約 1.29 ms（1.3×） | ほぼ無し。F16C 命令で変換できる。単体での最大誤差 3×10⁻⁴ |
| B2. int8（32要素ごとにスケール） | 約 10.4 MB | 約 0.21 ms | 161 µs | 約 1.12 ms（1.5×） | 少しあり。AVX-VNNI で内積を計算できる。単体での最大誤差 0.013、argmax は一致 |
| B3. int4 | 約 5.2 MB | 約 0.11 ms | 未計測 | 約 1.01 ms（1.6×） | あり |
| **B4. 2段階の厳密な argmax** | 約 10.4 MB + 少数の行 | 約 0.21 ms | 未計測（int8 部分は B2 と同じ） | 約 1.12 ms（1.5×） | **greedy（`-t 0`）なら出力は完全に同じ** |
| B5. 語彙の絞り込み | 使う語彙の割合に比例 | 割合次第 | 未計測 | ― | 学習データに出てこないトークンは生成されなくなる |

- 単体ベンチマークでは読む量にほぼ比例して速くなった（fp16 で 0.55 倍、int8 で 0.24 倍）。ただし単体ベンチマークは同じ行列を繰り返し読むので、10.4MB や 18.4MB の重みの一部が L3 に残り、速めに出る。`run.c` では他の層の重みで追い出されるので、見積もり（48.5 GB/s で割った値）の方が近いと考える
- A3 と組み合わせられる。単体では P4X の int8 で 75〜85 µs

- 出力層を削るほど、層の部分（P4_HT で 0.90 ms、うち固定コスト約 0.32 ms）の比率が上がる。B2/B4 の後は forward の約 8 割が層の部分になるので、A4 や層の重みの量子化（第5節）の重要度が上がる。A4 (a) で固定コストが 1.5 µs/回になれば、層の部分は約 0.65 ms になる見込み

### B4. 2段階の厳密な argmax

1. int8 の近似値で、32000 語すべてのスコアを計算する
2. 量子化の誤差には上限があるので、各行の「真の値の範囲」（上限と下限）がわかる
3. 上限が、近似値の1位の下限以上になる行だけを候補として残す
4. 候補の行だけを fp32 で計算し直し、argmax を取る

greedy の結果は量子化しない場合と完全に一致する。ベンチマークは `-t 0` で stdout の sha256 を比べているので相性がよい。top-p サンプリングにも応用できるが、その場合は確率の誤差を別途見積もる必要がある。

### B5. 語彙の絞り込み

TinyStories は簡単な英語の物語なので、Llama 2 の語彙 32000 のうち実際に使われるのは一部だけのはず。どれくらい絞れるかは、`tinystories.py pretokenize` で学習データを処理し、トークン頻度を数えて決める。

### 実装上の注意

- 埋め込み表として使う fp32 の元データは残し、出力層用に量子化したコピーを別に作る（埋め込み表は1トークンにつき1行しか読まないので、速度に影響しない）
- `runq.c` は全重みを int8（Q8_0）に量子化する既存の実装なので、B2 の簡易的な比較対象として使える

## 5. このマシン特有の狙い：モデル全体を L3 に収める

1トークンあたりに読むデータ全体が L3 に収まれば、2トークン目以降はほとんど DRAM を読まずに済む。単体ベンチマークでは、L3 に収まると帯域は約 2.3 倍（約 115 GB/s 対 約 50 GB/s）になった。ただし L3 は 12MB でも、**実際に収まる目安は 10MB 未満**（2 節）。

| 構成 | 1トークンで読むデータ量 |
|---|---|
| 現状（層の重み 23.9 + 出力層 36.9 + KV キャッシュ 最大3.5） | 約 64 MB |
| 層の重みを int8（約6.8）+ 出力層を int4（約5.2）+ KV キャッシュを fp16（1.8） | 約 13.8 MB（**目安の 10MB 未満まで約 4MB 足りない**） |
| 上の構成 + 語彙の絞り込み（B5） | 出力層（int4）を約 1.4MB 以下、つまり語彙を 3 割程度まで絞れれば 10MB 未満に収まる |

- 単体ベンチマーク（P4_HT、fp32、同じ行列を繰り返し読む）で、データ量と帯域の段差を確認した。8MB までは約 115 GB/s、10MB で 105 GB/s、12MB で 87 GB/s、16MB 以上で 63 GB/s 以下
- L3 は P コアと E コアで共有しているが、LP-E コア（CPU 12, 13）は別のタイルにあるので共有していない
- KV キャッシュの読み込み量は、生成が進むほど（`pos` が大きくなるほど）増える
- L3 に収まって帯域の制約が外れると、1.2 節の呼び出しごとの固定コストがそのまま残る。この狙いと A4（特に `OMP_WAIT_POLICY=active`）は組み合わせて考える

## 7. 計測についての注意

- **ステージごとの計測は `-DSTAGE_TIMING` で行う**（対応済み）。forward の中では配列に記録するだけで、出力は生成が終わってからまとめて行う。計測コードの影響は tok/s で P1 +0.2%、P4_HT +0.5%
- **周波数と電力を記録する**（対応済み）。`perf stat` の cycles ÷ task-clock と、turbostat の Bzy_MHz / PkgWatt / PkgTmp を全実行で記録している。このマシンでは cycles が `cpu_core` と `cpu_atom` に分かれて出る
- **トポロジーを結果と一緒に保存する**（対応済み）。`bench_memopt/env/` を毎回の結果フォルダにコピーしている。`lscpu -e` の L2 欄は CPU 8, 10 で壊れて表示されるので、`cache_sharing.txt`（sysfs から取得）を見る
- **関数とループの配置を 64 バイトに揃えてビルドする**。揃えないと、機械語が同じでも配置の違いだけで P1 の速さが約 10% 変わる。最適化案の効果を比べるビルドはすべて `-falign-functions=64 -falign-loops=64` を付ける
- **AC 電源につなぎ、EPP を performance にする**。バッテリー駆動ではスレッドを増やしたときに周波数が下がった（動作確認時、P4_HT で 3.84 GHz）
- **ブラウザなどを閉じて計測する**。Step 2 の 1 回目はブラウザを開いたまま計測し、ばらつきが 10% を超える条件が 11 個出た。閉じて再計測すると 7 個に減り、ばらつきの中央値も 2.8% → 1.7% になった（残りは L3 の境目や数 µs の短い計測など、原因がわかっているもの。`プロジェクト/progress-2026-10-15.md` 3.6 節）
- **単体ベンチマークの値の偏りに注意する**。P1 の値は `run.c` の中より遅く出る（mmap のままの fp32 で 1.65 ms 対 1.25 ms、原因未解明）。P4_HT は整合している（726 µs 対 760 µs）。また、同じ行列を繰り返し読むので、10MB 前後以下のデータは L3 に残って速めに出る
- **他のプロセスの負荷に注意する**。P2（CPU 0, 2）は HT の相方（CPU 1, 3）を空けているので、そこで別のプロセスが動くとコアの資源を直接取り合う。ベースライン計測で P2 だけばらつきが 5.2% になり、遅い回ほど計測に使っていない CPU の Busy% が高かった
