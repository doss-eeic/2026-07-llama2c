# 出力層（classifier）のメモリ最適化方針

対象マシン（Intel Core Ultra 5 225U）に限定して、stories15M 推論の最大の律速である出力層のメモリアクセスを最適化するための方針メモ。

- 計測データの出典: `dev/wataru` ブランチの `benchmark_affinity_stories15M/`（2026-10-12 計測、Linux、`make runomp`、`-n 256 -t 0 -s 42 -i "Once upon a time"`）
- 見積もりはすべて「処理時間は読み込む重みのバイト数に比例する」という仮定に基づく概算であり、実測で確認が必要

## 1. 前提：何が律速か

### 1.1 forward の内訳

| ステージ | 1トークンで読む重み | parallel region/token | P1 (ms) | 割合 | P4_HT (ms) | 割合 |
|---|---|---|---|---|---|---|
| **final**（`wcls` 32000×288） | **36.9 MB** | 1 | 2.627 | **54%** | 0.793 | **49%** |
| ffn_up（w1, w3） | 10.6 MB | 12 | 0.799 | 17% | 0.296 | 18% |
| qkv（wq, wk, wv） | 6.0 MB | 18 | 0.529 | 11% | 0.226 | 14% |
| ffn_down（w2） | 5.3 MB | 6 | 0.462 | 10% | 0.148 | 9% |
| attention_output（wo） | 2.0 MB | 6 | 0.205 | 4% | 0.076 | 5% |
| compute_attention | （KV キャッシュ） | 6 | 0.188 | 4% | 0.069 | 4% |
| norm / RoPE / SwiGLU / embedding | ― | ―（直列） | 0.019 | <1% | 0.018 | 1% |
| **forward 合計** | **60.8 MB** | **49** | 4.832 | | 1.628 | |

- P1 = P コア1スレッド（CPU 0）、P4_HT = P コア2つ＋HT（CPU 0-3、現時点の最速構成）
- matmul が forward の 91〜96% を占め、そのうち約半分が出力層
- 読み込んでいるのはトークンではなく**重み行列 `wcls`**。stories15M では埋め込み表と共有している（`memory_map_weights` の `shared_weights`）

### 1.2 メモリ律速と判断した根拠

- 処理時間が重みのバイト数にほぼ比例する（qkv/wo の時間比 2.95 に対して重みの比 3.0、ffn_up/ffn_down は時間比も重みの比も 2.0）
- 1トークンごとに 60.8MB の重みを読み直すが、L3 は 12MB しかないため、毎回 DRAM から読み込んでいる
- 計算量は 1 バイトあたり 0.5 FLOP しかない
- HT を足すと 1.45 倍速くなる（P2 → P4_HT）。メモリ待ちの間にもう1つのスレッドが読み込みを進められる、という特徴と合う

## 2. 対象マシンの特性

| 項目 | 値 |
|---|---|
| CPU | Intel Core Ultra 5 225U（P コア2つ（HT 付き）、E コア8つ、LP-E コア2つ、14 スレッド） |
| L2 | P コアごとに 2MiB、E コアは 4コアのクラスタごとに 2MiB を共有（cluster_a = CPU 4-7、cluster_b = CPU 8-11） |
| L3 | 12MB（P コアと E コアで共有） |
| DRAM | DDR5-5600 × 2ch、理論帯域 **89.6 GB/s** |
| SIMD 命令 | AVX2, FMA, F16C, AVX-VNNI（AVX-512 なし） |
| 出力層の実効帯域 | P コア1つ 14 GB/s、P4_HT 46.5 GB/s（理論値の約 52%）、E コアは最大でも約 22 GB/s |

**DRAM 帯域はまだ半分ほど残っている。** コア側が同時に出せるメモリ要求の数で頭打ちになっていると見られる。そこで改善の方向は次の2つ。

- **A. 読み込み方を改善する**：同じ 36.9MB を、より高い帯域で読む
- **B. 読む量を減らす**：バイト数そのものを削る

## 3. A. 読み込み方の改善（ロスレス）

どの案も出力が変わらないので、stdout の sha256 が一致するかで正しさを確認できる。

| 案 | 内容 | 期待できる理由 |
|---|---|---|
| A1. huge page | 重みを `mmap` から匿名メモリにコピーし、`madvise(MADV_HUGEPAGE)` で 2MB ページに載せる | 今は 4KB ページで、36.9MB は約 9000 ページになる。ハードウェアのプリフェッチャーは 4KB 境界を越えないので、境界ごとに先読みが途切れている。TLB ミスも減る |
| A2. 複数行を同時に処理 | `matmul` の内側で 4〜8 行を同時に計算する／ソフトウェアプリフェッチを入れる | 1コアあたりの同時メモリ要求数が増える。P コア1つで 14 GB/s しか出ておらず、伸びしろがある |
| A3. 出力層だけ P+E で分担 | 出力層の行を帯域比（P4_HT 約46 : E コア約20）で重み付けして配る | 出力層は行数が多いので同期コストが小さく、E コアの帯域を足し込める。上限は約 89 GB/s |

A3 の注意点：

- OpenMP の既定のスケジュール（均等分割）のままでは、遅い E コアを全員が待つ。P2E2（CPU 0,2,4,5）は P1 より遅かった
- E コアは1クラスタを全部使うと遅くなる（A3 4.89 ms → A4 6.27 ms）。クラスタにまたがって配置する（例：X4_2_2）
- U シリーズは消費電力の上限が 15W 前後なので、E コアを動かすと P コアのクロックが下がる可能性がある。周波数も記録して確認する

## 4. B. 読む量の削減

見積もりは P4_HT の帯域 46.5 GB/s を使った。

| 案 | 出力層の重み | 出力層の時間 | forward | 精度への影響 |
|---|---|---|---|---|
| 現状 fp32 | 36.9 MB | 0.79 ms | 1.63 ms | ― |
| B1. fp16 / bf16 | 18.4 MB | 約 0.40 ms | 約 1.24 ms（1.3×） | ほぼ無し。F16C 命令で変換できる |
| B2. int8（32要素ごとにスケール） | 約 10.4 MB | 約 0.22 ms | 約 1.06 ms（1.5×） | 少しあり。AVX-VNNI で内積を計算できる |
| B3. int4 | 約 5.2 MB | 約 0.11 ms | 約 0.95 ms（1.7×） | あり |
| **B4. 2段階の厳密な argmax** | 約 10.4 MB + 少数の行 | 約 0.22 ms | 約 1.06 ms | **greedy（`-t 0`）なら出力は完全に同じ** |
| B5. 語彙の絞り込み | 使う語彙の割合に比例 | 割合次第 | ― | 学習データに出てこないトークンは生成されなくなる |

### B4. 2段階の厳密な argmax

1. int8 の近似値で、32000 語すべてのスコアを計算する
2. 量子化の誤差には上限があるので、各行の「真の値の範囲」（上限と下限）がわかる
3. 上限が、近似値の1位の下限以上になる行だけを候補として残す
4. 候補の行だけを fp32 で計算し直し、argmax を取る

greedy の結果は量子化しない場合と完全に一致する。ベンチマークは `-t 0` で stdout の sha256 を比べているので相性がよい。top-p サンプリングにも応用できるが、その場合は確率の誤差を別途見積もる必要がある。

### B5. 語彙の絞り込み

TinyStories は簡単な英語の物語なので、Llama 2 の語彙 32000 のうち実際に使われるのは一部だけのはず。どれくらい絞れるかは、`tinystories.py pretokenize` で学習データを処理し、トークン頻度を数えて決める。

### 実装上の注意

- 埋め込み表として使う fp32 の元データは残し、出力層用に量子化したコピーを別に作る（埋め込み表は1トークンにつき1行しか読まないので、速度に影響しない）
- `runq.c` は全重みを int8（Q8_0）に量子化する既存の実装なので、B2 の簡易的な比較対象として使える

## 5. このマシン特有の狙い：モデル全体を L3 に収める

1トークンあたりに読むデータ全体が L3 の 12MB に収まれば、2トークン目以降はほとんど DRAM を読まずに済む。

| 構成 | 1トークンで読むデータ量 |
|---|---|
| 現状（層の重み 23.9 + 出力層 36.9 + KV キャッシュ 最大3.5） | 約 64 MB |
| 層の重みを int8（約6.8）+ 出力層を int4（約5.2）+ KV キャッシュを fp16（1.8） | 約 13.8 MB（**12MB のわずかに外**） |
| 上の構成 + 語彙の絞り込み（B5） | 12MB に収まる可能性あり |

- 読むデータ量と処理時間の関係をグラフにすると、12MB 付近で段差が出るはず。これを実測で確かめる
- L3 は P コアと E コアで共有しているが、LP-E コア（CPU 12, 13）は別のタイルにあるので共有していない
- KV キャッシュの読み込み量は、生成が進むほど（`pos` が大きくなるほど）増える

## 6. 進め方

1. **このマシンの上限を測る**：出力層だけを取り出した単体ベンチマークを作り、データ形式（fp32/fp16/int8）、ページサイズ（4KB/2MB）、スレッドの配置、データ量（L3 の内側か外側か）を変えて GB/s と ms を測る。どの案にどれだけ伸びしろがあるかを先に把握する
2. **ロスレスの A1〜A3 を `run.c` に入れる**：sha256 が一致することを確認しながら効果を測る
3. **B4（2段階の厳密な argmax）を試す**：出力を変えずに、読み込み量を約 1/3.5 にする
4. **必要に応じて量子化と L3 に収める構成へ進む**：B1〜B3、B5 と第5節

huge page の扱いは OS によって違うので、計測は Linux 環境で行う。

## 7. 計測についての注意

- 現在の計測コードは各ステージの間に `fprintf` が入っている。出力にかかった時間は計測から除いているが、キャッシュを汚したり、OpenMP の待機スレッドが休眠したりする影響は残っている可能性がある。出力層の最適化を評価するときは、ログを出さない計測モードも用意する
- CPU のクロック周波数を記録していないので、遅くなった原因が帯域なのか周波数低下なのかを切り分けられていない。`perf stat`（cycles）や `turbostat` を併用する
- コアのトポロジー（`lscpu -e`、`/sys/devices/cpu_core/cpus`、`/sys/devices/cpu_atom/cpus`）を計測結果と一緒に保存する
