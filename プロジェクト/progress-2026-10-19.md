# 出力層メモリ最適化 計測結果（2026-10-19）：B4（int8-exact）と OMP_WAIT_POLICY=active

方針: `プロジェクト/output-layer-memory-optimization.md`（以下「方針メモ」）
前回の進捗: `プロジェクト/progress-2026-10-15.md`

## 1. まとめ

- **B4（`-q int8-exact`、2段階の厳密な argmax）で、出力層は 0.756 → 0.254 ms（−66%）、forward は 1.660 → 1.139 ms（−31%）**（基準機の P4_HT）。出力は fp32 と完全に同じ（全 75 回で sha256 が一致）
- **`OMP_WAIT_POLICY=active` と組み合わせると forward 0.870 ms、1105 tok/s。既定の fp32（1.660 ms、589 tok/s）の 1.91 倍**。方針メモ 4.1 節の見積もり（約 0.86 ms）とほぼ一致した
- 2段目で fp32 で計算し直した行は、1トークンあたり平均 2.2 行、最大 29 行（全 32000 行中）。2段目のコストはほぼ無視できる
- 出力層が forward に占める割合は 46% → **28%** に下がり、残りの約 7 割は層の部分（0.62 ms）になった。この先の改善は層の部分が中心になる
- 判定で NG になったのは「P1 の計測コードの影響 +2.11%」の 1 項目だけ。遅い回は他の CPU の負荷が高く、バックグラウンドの負荷による可能性が高い（5.2 節）

## 2. 計測条件

| 項目 | 値 |
|---|---|
| 結果 | `bench_memopt/baseline/20261019_131313/` |
| コード | `7d50cb4`（dev/memory-opt）。`run.c` の `-q fp32\|fp16\|int8\|int8-exact` |
| マシン | 基準機（Intel Core Ultra 5 225U）、AC 電源、EPP performance |
| ビルド | `gcc -Ofast -fopenmp -march=native -falign-functions=64 -falign-loops=64`（計測ありは `-DSTAGE_TIMING`） |
| 推論 | `-n 256 -t 0 -s 42 -i "Once upon a time"`（222 トークン） |
| 集計 | 15 構成 × 5 回。先頭 16 トークンを除いたトークンごとの中央値を、5 回の中央値でまとめた |
| int8-exact のカーネル | AVX-VNNI（実行時に CPU を調べて選択） |

構成の名前: `_active` は `OMP_WAIT_POLICY=active`、`_int8x` は `-q int8-exact`、`_plain` は計測コードなし（tok/s のみ）。

### 3.2 B4（int8-exact）の効果

| 構成 | 出力層 (ms) fp32 → int8-exact | forward (ms) fp32 → int8-exact | 出力層の短縮 | forward の短縮 | 候補の行（平均 / 最大） |
|---|---|---|---|---|---|
| P1 | 1.219 → 0.458 | 2.286 → 1.555 | −62.4% | −32.0% | 2.2 / 29 |
| P4_HT | 0.756 → 0.254 | 1.660 → 1.139 | −66.3% | −31.4% | 2.2 / 29 |
| X4_2_2 | 0.863 → 0.280 | 1.882 → 1.269 | −67.5% | −32.6% | 2.2 / 29 |
| P4_HT_active | 0.746 → 0.244 | 1.371 → 0.870 | −67.4% | −36.5% | 2.2 / 29 |

- 読む量は 36.9MB → 10.4MB（約 0.28 倍）で、出力層の時間は 0.33〜0.38 倍になった。読む量の削減のほぼそのままの効果
- 候補の行数はスレッドの構成によらず同じ（同じ入力から同じ計算をしているため）
- 実効帯域は fp32 より下がった（P4_HT で 48.8 → 40.8 GB/s）。見積もり（48.5 GB/s で割った 0.21 ms）より 2 割遅い。x の量子化（1 スレッド）、誤差の上限の計算、2段目の並列区間の分が乗っていると考えられる
- **P1 では int8-exact の出力層が 22.6 GB/s しか出ていない**（fp32 の P1 は 30.2 GB/s）。1 スレッドでは int8 の計算そのもの（1 行ずつの処理）が律速に近い可能性がある。単体ベンチマークの P1 の int8 は 317 µs で、今回の 458 µs より速い
- 層の部分も少し変わった（P4_HT で 0.900 → 0.877 ms、P1 で 1.067 → 1.092 ms）。出力層の読み込みが減ったことでキャッシュの状態が変わった影響と考えられるが、確認はしていない

## 4. 正しさの確認

### 4.1 ベンチマーク

全 75 回（15 構成 × 5 回）で、stdout の sha256 が `golden.sha256`（master の `run.c`）と一致した。int8-exact の 20 回も含む。

### 4.2 計測前の確認（`eval_cls`、P4_HT、4 プロンプト × 256 ステップ）

| 項目 | 結果 |
|---|---|
| int8-exact の argmax が fp32 と一致 | 867 / 867 位置 |
| 候補の行の値が fp32 の matmul とビット単位で同じ | 差 0 / 1932 行 |
| 誤差の上限を超えた行 | 0 / 2774 万行。実際の差は上限の最大 14.4% |
| int8-exact で greedy 生成したトークン列が fp32 と同じ | 4 / 4 プロンプト |
| fp16 の logits の誤差 / argmax の一致 | 最大 0.0115 / 866 / 867 |
| int8 の logits の誤差 / argmax の一致 | 最大 0.314 / 863 / 867 |
| fp16・int8 で greedy 生成したトークン列が fp32 と同じ | それぞれ 3 / 4 プロンプト |

- fp16・int8 が一致しなかったのは "Tom and his dog went to the park" で、最初の 1 トークンから違う文になった（fp32 は「.」、fp16・int8 は「with Mom」）。logits が僅差の位置で、出力が変わる B1・B2 では起こりうる
- ビルドの組み合わせ（`-march=native` あり / なし、OpenMP なし、計測あり）× 構成（P1 / P4_HT / X4_2_2）× 形式（fp32 / int8-exact）の 24 通りで、sha256 が golden と一致した。`-march=native` なしでビルドした `eval_cls` でも int8-exact の確認は OK
- `test.c` も ALL OK

### 5.2 P1 の計測コードの影響（+2.11%）の注記

| 回 | P1（計測あり）tok/s | 他の CPU の Busy% | P1_plain（計測なし）tok/s | 他の CPU の Busy% |
|---|---|---|---|---|
| 1 | 430.0 | 3.37 | 433.3 | 1.05 |
| 2 | 423.4 | 3.41 | 420.2 | 2.89 |
| 3 | **406.2** | **4.55** | 433.3 | 1.29 |
| 4 | **408.5** | **3.99** | 432.5 | 1.67 |
| 5 | 432.5 | 0.73 | 429.1 | 2.37 |

- 計測ありが遅かった 3・4 回目は、計測に使っていない CPU の負荷も高かった。1・2・5 回目の差は ±1% 以内
- 2026-10-13 のベースラインでは P1 の影響は +0.19% だった。計測コードは変えていないので、今回の NG はバックグラウンドの負荷によるものと考えられる
- 結論への影響はない（B4 と `active` の効果はこのぶれより一桁大きい）

### 5.3 平均周波数の注記

int8-exact の構成は perf の平均周波数がやや低い（P4_HT で 4.59 → 4.48 GHz、X4_2_2 で 3.65 → 3.57 GHz）が、turbostat の Bzy_MHz は fp32 と同じ（P コア 4.8 GHz）。perf の値はプロセス全体の平均なので、読み込み時の量子化（1 スレッド）などの区間が入った影響と考えられる。forward の時間には影響していない。

## 6. 未計測・残っている課題

- **B1（fp16）と B2（int8）の速さは `run.c` で測っていない**。`run_baseline.sh` の構成に入っていないため（精度は 4.2 節で確認済み）。ベンチマークのプロンプトでは fp16・int8 も fp32 と同じ出力になるので、構成を足せば sha256 の確認も通る（ただし、このプロンプトでたまたま一致しているだけ）。集計スクリプトの比較は `_int8x` にしか対応していないので、`_fp16` / `_int8` にも広げる必要がある
- **誤差の上限の余裕 `CLS_BOUND_MARGIN`（1/64）が dim によらず固定**。浮動小数点の丸めの最悪値は dim に比例して大きくなり、dim が約 500 を超えるモデル（stories42M 以上）では最悪の場合を保証できない。実際の差は上限の 14% 程度なので破れる可能性は低いが、任意のモデルで厳密にするには、余裕を dim から決める形にする
- **2段目の値が fp32 の matmul とビット単位で同じになるかはコンパイラの最適化しだい**。GCC 13 では確認できた。コンパイラやフラグを変えたら `eval_cls` の [3] で確認する
- **int8-exact の出力層の効率**（3.2 節）。P4_HT で見積もりより 2 割遅く、P1 では fp32 より実効帯域が低い。x の量子化の並列化、2段目を1つ目の並列区間に入れる（起こし直しを 1 回減らす）、4 行同時の int8 カーネル、などで改善できる可能性がある
- 出力層の割合が 28% まで下がったので、次の大きな対象は層の部分（P4_HT_active で 0.62 ms、forward の 71%）。層の重みの量子化（方針メモ第5節）や A4 (b)（並列区間をまとめる）が候補
