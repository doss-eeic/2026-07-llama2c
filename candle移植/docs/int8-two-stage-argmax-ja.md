# Int8 two-stage argmax（stories15M）

`llama2-c` の greedy 生成で、最後の出力射影と argmax を Int8 の 2 段階選別に置き換えました。この文書では、その実装の差分と stories15M での測定結果をまとめます。生成されるテキストは f32 の場合と同じまま、cache 入りのビルドに対して生成速度が **+39.8%**（中央値 347.1 → 485.1 token/s）上がりました。

## 実装の差分

変更はコミット `d075fd55` に入っています。対象は次の 3 ファイルです。

| ファイル | 変更内容 |
| --- | --- |
| `candle-transformers/src/models/llama2_c.rs` | `forward` を分割し、最終 norm までを計算する `forward_hidden` と、`lm_head` の重みを返す `lm_head_weight` を追加 |
| `candle-examples/examples/llama2-c/classifier.rs` | 新規作成。`Int8Classifier`（llama2.c fork の `src/classifier.h` を移植したもの） |
| `candle-examples/examples/llama2-c/main.rs` | `--two-stage-argmax` と `--group-size`（既定値は 32）を追加し、推論ループで分岐 |

### 変更前の流れ

```
hidden → lm_head (f32 matmul, vocab×dim) → logits を f32 に変換 → LogitsProcessor で argmax
```

1 トークンごとに、語彙 32,000 行のロジットをすべて f32 で計算していました。

### 変更後の流れ

```
hidden → Int8Classifier::argmax(hidden)
  1. 全行を Int8 で近似計算し、各行の上限と下限を求める（rayon で 64 行ずつ並列）
  2. 上限が「全行の下限の最大値」以上の行だけを候補に残す
  3. 候補行だけを f32 で計算し直し、その中の argmax を返す
```

- **量子化（読み込み時に 1 回だけ）:** `lm_head` の重みを、行ごと・`gs` 要素ずつのグループに分けます。各グループで `scale = max|w| / 127` を求め、重みを `i8` に丸めます。
- **誤差の上限:** 行ごとに `err = 0.51 × Σ_g scale_g × Σ|x_g| + 1e-6` とします。丸め誤差は 1 要素あたり最大 0.5 × scale なので、0.51 は C 実装と同じ少し大きめの余裕です。
- **結果が正確な理由:** 本当の最大値を持つ行は、上限が必ず全行の下限の最大値以上になるため、候補から外れません。f32 での計算し直しは候補行だけに行い、その中の最大を選びます。そのため選ばれるトークンは、f32 で全行を計算した場合と同じになります。
- **使える条件:** `--temperature 0` と `--repeat-penalty 1` の greedy 生成で、gguf ではないモデルに限ります。それ以外の条件では起動時にエラーになります。

```rust
// classifier.rs: 各行の近似値と誤差の上限
for g in 0..ng {
    let mut dot = 0f32;
    for (q, x) in q[g * gs..(g + 1) * gs].iter().zip(&x[g * gs..]) {
        dot += *q as f32 * x;
    }
    approx += dot * s[g];
    bound += s[g] * a[g];
}
let err = 0.51 * bound + 1e-6;
(approx + err, approx - err)
```

## 測定

### 条件

- **CPU:** Intel Core Ultra 5 225U（14 論理 CPU）
- **モデル:** `data/stories15M.bin`（dim 288、語彙 32,000）
- **生成条件:** プロンプト `Once upon a time`、256 トークン、temperature 0、repeat penalty 1
- **スクリプト:** `benchmarks/cpu_inference_matrix.py`
  - `--cache-rounds 10 --group-rounds 20 --scaling-rounds 0 --group-sizes 32`
- **反復:** 6 セッション実行しました。セッション 1〜3 は 2026-10-27 16:30〜16:35、セッション 4〜6 は同日 17:39〜17:43 に、それぞれ続けて実行しています。各ラウンド内で条件の実行順はランダムです。

- **データ:** `docs/results/cpu-inference-15m-session{1..6}-2026-10-27.csv`

## 考察

- **cache と argmax の効果は別々に足し合わさります。** upstream 既定 112.2 → cache 349.5 で 3.1 倍（スレッド数の解決をキャッシュした効果）、そこから Int8 argmax で 485.1 になり、合計 4.3 倍です。
- **出力射影が速くなった分が効いています。** stories15M はモデルが小さく、1 トークンあたりの計算のうち語彙 32,000 × dim 288 の `lm_head` が大きな割合を占めます。Int8 の近似計算と、少数の候補行だけの計算し直しに置き換えたことで、その分が短くなりました。
- **グループサイズは 24〜48 ならほぼ同じです。** 以前の測定（`cpu-inference-2026-10-27.csv`、`cpu-inference-15m-focused-2026-10-27.csv`）では、g24〜g48 の差は数 % 以内でした。一方、g1〜g3 は f32 より遅いか同じくらいでした。グループが小さいとスケールの計算が増え、ベクトル化も効きにくくなるためだと考えられます。
- **スレッドが少ないと逆に遅くなります。** 以前の scaling 測定では、Int8 は 1 スレッドで 219.5 token/s と f32（346.4）より遅く、8〜10 スレッドで最も速くなりました（約 491〜494）。並列化が前提の実装です。
- **モデルが大きいと効果は小さくなります。** stories42M で 3 回だけ測った参考値は +18% でした。モデルが大きいほど、計算全体に占める出力射影の割合が下がるためです。

## 注意点

- セッション 1〜3 と 4〜6 は約 1 時間空けて実行し、どちらも同じ傾向でした（改善率 +37.6〜+42.0%）。それ以上の時間帯やマシンの温度による変動は確かめていません。
- 同じ日の別の実行では、f32 が 266 token/s と低く出て、改善率が +17% になったことがあります（マシンに負荷がかかっていたと考えられます）。測定するときは、マシンを何も動かしていない状態にしてください。
- 改善率は token/s での値です。モデルの読み込みを含むプロセス全体の時間では 0.880 s → 0.718 s で、約 18% の短縮です。
