# 1〜14論理CPUの探索とアプローチ比較（2026-10-22）

[全結果・試行記録](../../results/topology14_oracle_20261022/README.md)と
[実験計画・実行仕様](../../src/cpuprofiler/TOPOLOGY14.md)が今回の入口。
計3,551測定を行った。前回のP必須・E偶数等の制約を外し、
Pなし、P片側のみ、片側SMT、奇数E、LP-Eを含め、層内人数1〜14を全て実測した。

## 空間と実施内容

同種P物理コア間、EのL2共有群間、各群内のCPU交換をまとめる。
SMT関係と「同じL2に何人、別のL2に何人」は保持し、P/E/LP-Eは区別する。

|対象|元の組合せ|同値化後|今回の測定|
|---|---:|---:|---|
|固定mask|16,383|269|全代表×2 backend×3ブロック|
|層内⊆outputのmask|4,766,585|14,850|全型を定義し、適応探索|
|mask×backend/層分配/1・4行|―|118,800|5手法×2seed×112照会|

全118,800候補を総当たりしたとは主張しない。
QKV/FFN融合とoutput dynamic32物理行、p_weight1は固定。
固定269型のoracleは層dynamic16・output1行の538候補に限定する。
全16,383部分集合が269型へ写像されることと、14,850入れ子型の往復をテストした。

|フェーズ|候補/比較測定|control|warmup|合計|
|---|---:|---:|---:|---:|
|固定oracle・交換点検・参照|1,707|111|2|1,820|
|実測探索5手法×2seed|1,120|71|2|1,193|
|独立確認65条件×8ブロック|520|16|2|538|

## 試した5手法

全手法が初期14点で1〜14人を必ず測定し、観測済みの最良点だけを推薦する。
探索器に固定oracleの速度を渡していない。

- **random**: 同値類の一様探索。
- **beam14**: 初期14点後、深さ1〜14へ各7照会。上位3層内配置からCPUを追加し、output拡張・kernelも選ぶ。
- **hierarchical**: 56点まで人数で層別化した固定配置探索、その後は有力層内配置のoutputとkernelを探索。
- **model_counts**: P/E/LPの合計人数中心の逐次ridge予測器。
- **model**: SMT物理構造とL2群の占有分割も使う40特徴の逐次ridge予測器。

モデルは大域候補と最良点のグラフ近傍から最大256点を提案し、5回に1回は一様探索する。
2つのモデルは同じ候補表現・提案方式で、予測に使う特徴を変えた。
**beam14の成長過程そのものも、両seedで深さ14まで完了**した。

独立確認での推薦1点のlatency差（全確認候補内の最良平均を基準、2seed平均）:

|手法|確認時の平均gap|2seedの範囲|候補run秒計（224照会）|
|---|---:|---:|---:|
|random|5.25%|2.61〜7.88%|117.29|
|beam14|4.77%|2.12〜7.43%|123.49|
|hierarchical|4.19%|3.51〜4.86%|120.69|
|model_counts|3.24%|1.76〜4.73%|101.51|
|model|4.41%|4.01〜4.82%|104.36|

2seedのみなので、小差や一般的な手法の優劣は確定しない。
今回は人数中心のモデルが比較的良く、予測特徴へのL2/SMT追加の利点は明確でなかった。
L2情報を同値化・候補生成に使うことと、予測器の特徴を増やすことは分けて評価する。

固定538候補ではleave-one-block-out、各10seed、28/56/112/168照会のreplayも行った。
112照会の平均regretはrandom14.32%、beam14 12.06%、hierarchical9.99%、
model_counts9.80%、model9.69%。訓練538候補の全探索も9.61%だった。
評価ブロックの最良値の変動が大きく、点数を増やせば未使用ブロックでも必ず速くなるとは限らなかった。
30replayは同じ3実測ブロックの再利用であり、30独立実験ではない。

## 14人まで測った結果

固定kernelの全配置比較では、**P論理3＋E6の9人**が最速平均795.52 tok/sだった。
この片側SMT構成は前回の探索空間にはなかった。
ただし以下の独立確認とは測定フェーズ・kernel条件が異なるので絶対速度を混ぜない。

独立確認では全14人の全8kernel設定×標準/交換の2種類のCPU rank順も、各8回測定した。

|独立確認の構成|平均tok/s|
|---|---:|
|前回の採用候補: pthread、層P4E4の8人→output12人、層static/output dynamic32、1行|798.24|
|未改造qkv-ffnブランチ、P4E4|772.81|
|未改造upstream、P4E4|675.91|
|全14人の16条件中の最良: OpenMP、dynamic、1行、交換rank順|631.63|

今回の最速平均構成は前回と同一。設定は
[best_config.json](../../results/topology14_oracle_20261022/best_config.json)。
層CPU=`(0,2,1,3,4,5,8,9)`、outputに`(6,7,10,11)`を追加する。
upstream比の速度改善はブロック内latency比で18.06%、探索的95%区間[14.83,21.95]%。
qkv-ffn比は3.23%、区間[-0.28,7.36]%で改善は未確定。
前回の824.03 tok/sと今回の798.24 tok/sは、別フェーズなので実装差として比較しない。

## 同値化の精査・失敗と限界

代表とP/E/LP群を交換した28配置を測った。
3ブロックの算術平均差には大きな外れ値があり、交換差の絶対値の中央値は4.67%、最大222.94%。
単発の極端な遅延を含むため、物理CPU差だけが原因とはみなさない。
外れ値は除外せず、ブロック別の値とセル中央値からの診断フラグを保存した。

同種CPUの同値化は性能上の厳密な等価性ではない。
そこで各実測探索の上位1と固定oracle上位2は、交換代表も独立確認に含めた。
CPU群だけでなくrank順序が変わる影響もある。
全CPU順列・全代表を確認したわけではないため、真のCPU番号単位の大域最適は保証しない。

今回の実用的な方針は「合計人数中心の軽い探索→有力同値類のCPU代表交換→独立確認」。
既知の採用候補も保持し、確認で上回るまでは置き換えない。
CPU数を途中で制限せず14まで見た上で、今回は8→12人が残った。
大型モデル・長文・別CPU、任意chunk・重み・バリア方式は未検証。
