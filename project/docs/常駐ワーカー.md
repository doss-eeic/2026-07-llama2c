# 常駐ワーカー（SECTION_WORKERS=pool）

split-beam（`-B` / `-C`）で出力層とそれ以外（body）の CPU を分けたとき、OpenMP では区間の切り替えと同期のコストが大きく、CPU を分けた効果が出なかった。
起動時に CPU ごとに 1 本ずつスレッドを作り、固定したまま使う常駐ワーカーに置き換えて解決した。

ブランチ: `feature/cpu-profiler-stay-team`

## omp parallel の仕組み

### 仕様

`#pragma omp parallel num_threads(N)` について、OpenMP の仕様は次のように決めている。

- チームの N 本全員が、領域の中身を実行する。仕事を割り振るかどうかは中身のコード（`if (tid < 2)` や `omp for` の分け方）次第で、仕事がなくても N 本全員が中身を通る。
- 領域の最後には暗黙のバリアがあり、チームの全員が着くまでだれも先に進めない。
- `omp for` などの作業分担の構文は、チームの全員が通るか、だれも通らないかのどちらかでなければならない（一部のスレッドだけでは回せない）。

### libgomp のスレッドの使い回し

libgomp は、一度作ったスレッドをプールに残し、次の parallel 領域で使い回す。新しく作るのは、チームの本数が前より増えたときだけ（減ったときは余ったスレッドを終了する）。
プールのスレッドは、次のループを回り続けている。

```
for (;;) {
    待機場所で待つ            ← 領域と領域の間はここにいる（スピン → しばらくすると眠る）
    渡された関数を実行する     ← parallel 領域の中身（仕事がなければすぐ終わる）
    領域の終わりのバリアに着く ← 全員がそろうまで待つ
}
```

parallel 領域 1 つごとに、次のことが起きる。

1. 開始: メインスレッドが、チームの各スレッドに「実行する関数、引数、チームの情報」を書き込み、待機場所での待ちを解く。
2. 中身の実行: 仕事のないスレッドは、中身を通り抜けるだけ。
3. 終了: 全員がバリアのカウンタを 1 ずつ増やし、メインスレッドは全員がそろうまで待つ。
4. 各スレッドは待機場所に戻る。

スレッドを作り直すわけではないが、開始時の書き込みと待ちの解除、終了時のカウンタの更新は、仕事のないスレッドも含めたチームの全員について毎回起きる。
これらはコアの間でのキャッシュラインの受け渡しなので、本数が増えるほど時間がかかり、メインスレッドはいちばん遅いスレッドを待つことになる。

空に近い parallel 領域（仕事をするのは先頭 2 本だけ、仕事の量は同じ）で測ると、1 領域あたり、チーム 2 本で 3.6 µs、4 本で 4.8〜5.0 µs、6 本で 5.4〜5.7 µs だった。
body には 1 トークンあたり約 48 個の parallel 領域があるので、仕事のないスレッドが 2 本で約 +0.06 ms になる。

### 常駐ワーカーとの違い

| | OpenMP（libgomp） | 常駐ワーカー |
|---|---|---|
| スレッドの作成 | 最初と、チームの本数が増えたとき（減ると終了する） | 最初だけ |
| 1 つの領域で仕事を渡す相手 | チームの全員（仕様で決まっている） | 今の区間のワーカーだけ |
| 終わるのを待つ相手 | チームの全員 | 仕事を渡したワーカーだけ |
| 仕事のないスレッド | 毎回の受け渡しに加わる | 自分の待機場所で待ったまま、何にも加わらない |
| チームから外す方法 | 本数を減らすしかない（スレッドが終了する） | 区間の CPU に入れなければよい |

## OpenMP で起きていた現象

1 トークンの中で、区間は 2 回切り替わる（body → 出力層 → 次のトークンの body）。
`enter_section()` は区間に入るたびに、新しいスレッド数で parallel 領域を開き、各スレッドを `sched_setaffinity` でその区間の CPU に固定し直していた。

### 1. スレッドの終了と作り直し

libgomp は、parallel 領域のスレッド数が前より減ると余ったスレッドを終了し、増えると `pthread_create` で作り直す。
body 2 スレッド、出力層 6 スレッドの構成では、1 トークンごとに 4 スレッドを作って 4 スレッドを終了していた（64 トークンで `clone` が 257 回）。
新しいスレッドは、作った側（CPU 0 に固定）の CPU 指定を引き継ぐので、いったん CPU 0 で動き出してから本来の CPU へ移る。

### 2. スレッドの移動

スレッド i の行き先は、`-B` / `-C` の i 番目の CPU で決まる。
並び順によっては、同じスレッドが毎トークン CPU を行き来する（例: `-B 0,2 -C 0,1,2,3,7,9` では、スレッド 1 が CPU 2 ↔ 1 を行き来する）。

1 と 2 を合わせて、1 トークンあたり約 0.07〜0.08 ms（全体の 6〜7%）かかり、CPU を分けて得られる分（1〜2%）より大きかった。

### 3. スレッド数を揃えると、仕事のないスレッドまで同期に参加する

1 をなくすために、両方の区間のスレッド数を多い方に揃える方法を試した（`SECTION_TEAM=fixed`、`feature/cpu-profiler-fixed-team`）。
作り直しはなくなったが、仕事のないスレッドも parallel 領域の開始と終了の同期に参加する。body には 1 トークンあたり約 48 個の parallel 領域があるので（1 層に matmul 7 回と attention 1 回、6 層分）、body が 0.07〜0.15 ms 遅くなり、全体では前より遅くなった。
OpenMP の parallel 領域では、チームの一部だけで同期できないので、1 と 3 を同時にはなくせない。

### 4. parallel 領域ごとの同期が重い

区間の切り替えがない構成（`-B` と `-C` に同じ 6 CPU）でも、libgomp では body が 0.74 ms かかっていた。常駐ワーカーでは同じ計算が 0.51 ms で終わるので、差の約 0.23 ms は約 48 回の同期のコストと考えられる。

### 5. `OMP_SCHEDULE=dynamic,128` で、matmul が 3 つにしか分かれない

cpuprofiler は `OMP_SCHEDULE=dynamic,128` で計測していた。dim=288 の matmul は 128 行ずつだと 3 つにしか分かれないので、4 スレッド以上にしても 3 本しか働かない。
10/22 の「int8-exact は P コア 3 スレッドが最速」という結果は、この設定によるものだった（`static` にすると 6 CPU の方が速い）。

## 解決策

### 常駐ワーカー（`run.c`、`SECTION_WORKERS=pool`）

- 起動時に、`-B` と `-C` の CPU それぞれに 1 本ずつワーカーを作る。作る前に CPU を固定するので、最初からその CPU で動き出す。以後は作り直しも移動もしない（1、2 がなくなる）。
- メインスレッドは `-B` の先頭の CPU に固定し、自分の CPU が今の区間に入っていれば、その分を計算する。
- parallel 領域 1 つは、今の区間の CPU のワーカーにだけ、それぞれの受け取り口（別々のキャッシュライン）へ仕事を書いて渡す。終わるのを待つのも、そのワーカーだけ（3 がなくなる）。
- 待つときは、atomic で読みながら pause 命令でスピンする（4 が軽くなる）。
- 行は、区間の CPU で均等に分ける。1 行ごとの計算は OpenMP の場合と同じ関数なので、出力はビット単位で一致する（fp32 / int8-exact、16 通りで確認）。
- `SECTION_WORKERS` を指定しなければ、これまでどおり OpenMP で動く。

### cpuprofiler

- `-w pool` で常駐ワーカーを使う（例: `uv run cpuprofiler split -q int8-exact -w pool`）。全体の探索（`beam`）では、`-B` と `-C` に同じ CPU を渡す。
- `omp_schedule` の既定値を `static` にした（5 への対策）。
- split の区間の探索も、区間の ms ではなく全体の tok/s で評価する。区間の ms では、切り替えのコストが切り替えた先の区間のタイマーに入り、見えなくなるため。

## 結果（int8-exact、stories15M、256 トークン）

| 構成 | tok/s |
|---|---:|
| 10/22 の split（omp、`dynamic,128`） | 850.0 |
| beam（omp、`static`）の最速: (0, 1, 2, 3, 5, 8, 10, 11) | 1067.6 |
| **split（pool、`static`）**: body (0, 1, 2, 3, 4, 6, 8, 10)、出力層 (0, 1, 2, 3, 7, 9, 10, 13) | **1578.6** |

split（pool）の区間ごとの時間は、body が 0.429 ms/token、出力層が 0.175 ms/token。各構成を 1 回ずつ測った値。

## 残っている課題

- 待ち方がスピンだけなので、片方の区間にしかない CPU のワーカーは、もう一方の区間の間もスピンし続ける（HT の相方の計算資源を取る可能性がある）。少しスピンしたあと futex で眠らせ、区間が変わる直前に起こす方法が考えられる。
- 新しく pool で探索した構成が本当に最速かは、上位の構成を複数回測り直して確かめる必要がある。
