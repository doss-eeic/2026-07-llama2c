# 並列化の切り出しと実測選択

2026-10-20、`e78d28e`までを確認。Linuxでの新規計測や実行系の再実装は行っていない。

## 今回の問い

CPUトポロジー・電源設定・動作状態に応じて、起動前の実測から並列実行ポリシーを
選ぶことで、事前に固定した設定より安定して速くできるか。
本家からの変更を少なくするため、選択と記録はPython側、数値演算と仕事の分配は
小さなCモジュールに置く。現状はOpenMPを第一の実行方式とする。

環境による最適設定の変化は、実測選択が役立つ場面になる。ただし、過去の実験間では
実装・計測方法も変わっている。過去の順位逆転を気温・電源等の効果と断定せず、
同じバイナリを異なる条件で評価して実測選択の価値を検証する。

## 得られた知見

1. コア数だけでなく、SMT、Eクラスタへの配置、低電力コアの参加が性能に影響する。
   E4の2+2配置の優位性は複数実験で観察されたが、E2では分散が逆効果の場合もある。
2. QKV、FFN、outputで有利な構成が異なる。演算形状を使った候補生成に意味がある。
3. 旧stay2では重み2が有利、現在のstayでは均等が有利だった。P/Eの名称から比率を固定しない。
4. 現在は、融合とスケジューリングを変更したOpenMP版が有力。stayは比較用に残す。
5. 電源変更の申告があり、最新記録は性能優先設定。ただし旧条件との完全な比較はできない。
   気温や温度、電力制限の個別の寄与もまだ分離していない。

確認測定：計測なし、各10回、平均tokens/s。
出典：[rates.csv](../../results/cores_confirm_20261020_161145_042899/rates.csv)。

改善P4E4は同じCPU集合の本家比約11.3%高速。ただし融合とスケジュール等を同時に

8人・1行版と10人・4行版の約0.4%差から、10人が最適とは結論できない。
CPU数だけを比較する場合はoutputの計算方式も揃える。

## 切り出す境界

`run.c`のモデル構造、KV cache、Norm、RoPE、残差加算、生成処理は維持する。
演算群の呼び出しを次の3か所にまとめることを提案する。名前は現在の実装に合わせる。

```c
parallel_qkv(q, k, v, xb, wq, wk, wv, dim, kv_dim);
parallel_ffn(hb, xb, w1, w3, dim, hidden_dim);
parallel_output(logits, x, wcls, dim, vocab_size);
```

- QKV：本家の3つのmatmulをまとめる。GQAのdim/kv_dimの違いも扱う。
- FFN up/gate/SwiGLU：同じ行の2つの内積と要素演算をまとめる。
- output：通常行分割、チャンク取得、必要なら4行処理をこの関数内で選ぶ。
- 通常のmatmulとAttention：本家の並列ループを活用する。初回はチーム人数を共通に保つ。

QKVとFFNの融合は、並列領域の起動回数を減らすための小さな演算群の変更。
forward全体をワーカーごとに走らせる設計を、標準の切り出し方にはしない。

## 本家との差分を抑える構成案

| 置き場所 | 責任 |
|---|---|
| `run.c` | 上記3演算群の呼び出し、既存2並列ループの方針適用、必要な初期化 |
| `src/parallel.h`等のCモジュール | 数値カーネル、融合のON/OFF、行分配、output処理 |
| `src/cpuprofiler/` | トポロジー取得、候補作成、別プロセスの測定、選択・設定保存 |
| 別の計測ビルド | forward・層・演算群の時間。診断用で採用判断とは分ける |
| 固定revisionの本家 | 未改造の対照実装 |

現在の`run.c`にはstay・詳細計測・融合の実験経路が集まっている。
実験用ソースとログを保存したうえで、標準経路からstay用のSERIAL/SYNC/BEGIN/ENDや
forward二段dispatchを分離する。C側はTransformer全体を知る必要のない配列・次元のAPIにする。
本家追随のためにforward全体の手書きコピーをもう一つ作ることは避ける。

JSONの読み込み、CPU分類、最適設定の探索を`run.c`に入れない。
Python側が設定を選び、OpenMP初期化前にCPU集合・環境変数を適用して実行する。
最初は現在ある環境変数と起動引数を利用し、独自の大きなポリシー形式を作らない。
性能採用時にはヘルパー化によるコード生成の変化も測定し、差分行数だけで良し悪しを決めない。

## 探索するものを分ける

カーネルの選択：QKV融合、FFN融合、output1行/4行。
スケジューリングの選択：CPU集合・順序、人数、static/dynamic/guided、チャンク行数。
待機・電源条件：実験条件として記録し、同じ比較内では揃える。

最初は改善P4E4・output1行を固定対照とし、同じカーネルでCPU集合とチャンクを校正する。
8/10人、SMTの有無、Eクラスタ配置を少数の候補で比較する。
output人数の切替はチーム変更費用も含めて候補として評価し、既定では人数を変えない。
stay、P:Eの重み、Attentionだけの人数変更は、必要性が再確認された場合の追加実験にする。

チャンクは物理的な行数で定義する。現在の4行版ではchunk=32が128行に相当するため、
1行版のchunk=32との比較は、計算方式とチャンク行数の両方が変わっている。
カーネル効果の比較では同じ行数へ揃え、各方式の最良値の比較は別に実施する。

## 今回の実験

### A. 融合等の効果を確認する

CPU集合・人数・スケジュールを固定して、QKV融合とFFN融合を個別にON/OFFする。
現在のfuse一括スイッチだけでは個別の寄与を分離できないため、評価時に分ける。
output1行/4行はチャンク行数を揃えて比較する。チーム人数と計算方式を同時に変えない。

### B. 実測選択の価値を確認する

同じカーネル・バイナリを、ユーザーが設定した複数の電源モードや実際の動作条件で使う。
変更する条件を明示し、周囲温度・負荷中温度・周波数は取得可能な範囲で記録する。
ユーザーの実機設定をこちらで無断に変更しない。

各条件で以下を比較する。

1. 事前固定の設定（改善P4E4・output1行）。
2. 別条件で選んだ設定をそのまま再利用。
3. 現在の条件で短い校正を行い、独立した確認試行で評価。

未改造本家P4E4も同じブロックで測り、融合等の改善と校正の改善を別々に示す。
条件が変わっても勝者が変わらない場合も結果として残す。
実測選択の価値は、条件別最良値との距離、固定設定への改善、校正時間で評価する。

### C. 測定と再利用

- 同一の固定入力、モデル、正しさ基準、skip範囲を使用する。
- 各候補のウォームアップを揃え、全候補1回ずつのブロック内で順序をランダム化する。
- 校正と確認を分ける。細かい時計・センサー・PMU診断は別走行にする。
- 主指標は計測負荷を抑えたforward時間、生成tokens/sは別に併記する。
- 生ログ・ソース・バイナリ/モデルのハッシュ、コンパイラ、CPU配置、電源設定を保存する。
- 設定はCPU・利用可能CPU・モデル・バイナリ等に紐づけて再利用する。
  温度の瞬間値をそのままキャッシュキーにして設定を頻繁に切り替えることは避ける。
- 電源モード変更時や起動前の短い確認で性能が変わった場合、再校正を候補にする。
  毎トークンの探索・設定変更は今回の範囲に含めない。

校正コストは無視しない。回収に必要なトークン数の目安は、
「校正時間 ÷ 1トークン当たり短縮時間」。短い生成ごとの全探索は回収しにくいため、
設定を複数回の推論へ再利用する設計にする。

## 到達点

小さな演算モジュールとPythonのCPU-Profilerを組み合わせ、
本家の構造を保ったまま、現環境に合う設定を実測で選択・再利用できること。
最速コア数やP:E比を一つに決めることではなく、選択が必要になる条件とその費用を示す。
