# 現在のrun.cと未改造版の比較（2026-10-20）

現在のQKV・FFN融合版は、設定を明示すると未改造版より高速だった。一方、環境変数を省略した既定設定では遅くなる条件がある。今回の最速はP2E8の10スレッド・dynamic設定で744.31 tok/s、同じCPU配置の未改造版573.03 tok/sに対して29.9%向上した。全14論理CPUを使う構成は最速ではなかった。

## 比較対象と方法

- 現在版: `e02948e2450b37ff5290c35d7e0093fac967d3e8`。QKVの並列領域を統合し、FFNのup/gateとSwiGLUを融合したOpenMP版。
- 融合前: `666aa86490bbb61f1d0bab175e0c7ba6e08c45c4`。通常演算のruntime scheduleとoutput設定を既に備える。現在版との比較で融合の効果を評価する。
- 未改造版: `350e04fe35433e6d2941dce5a1f53308f87058eb` の `run.c` を変更せず使用。通常ループはruntime scheduleではなく、OUTPUT_*も解釈しない。

全版を同じ `gcc -Ofast -march=native -fopenmp` で新規ビルド。stories15M、256 steps、temperature=0、seed=42、prompt="Once upon a time"。各版を32 stepsでウォームアップ後、10条件×3版×10反復=300試行。各反復で条件順と、同一条件内の隣接した3版の順序をシャッフルした。各プロセスのtok/sを算術平均し、ms/tokenは各試行の逆数から別途平均した。生成された全文は300試行すべて同一SHA-256だった。

CPUはIntel Core Ultra 5 225U。P4=(0,2,1,3)は2個のPコアのSMT込み4論理CPU、P4E4=(0,2,1,3,4,5,8,9)は8論理CPU、P2E8=(0,2,4,5,6,7,8,9,10,11)はSMTを使わない10物理コア、All14はLP Eコアも含む14論理CPU。tasksetと明示的なOMP_PLACES、PROC_BIND=close、OMP_DYNAMIC=FALSEを使用した。

## 結果

単位は平均tokens/s。対未改造の角括弧は反復を対応させたブロックbootstrap 5,000回による95%区間（%）。各条件の反復数は10。

`static`は通常演算・outputともstatic、人数も同数。`dynamic`は通常dynamic,16、outputはdynamic,128で人数は同数。`P4_to_output8`は通常4/static→output8/dynamic,128。ただし未改造版はOUTPUT_*を無視するため4→4のままであり、同じ演算方式同士の比較ではない。

`defaults`はOMP_SCHEDULEとOUTPUT_*を省略した。今回のlibgompでは未設定のruntime scheduleはdynamic,1（同じ環境のプローブで確認）。現在版・融合前はこれを通常演算に使い、outputはソース既定の8/dynamic,128を使う。All14_defaultsは14→8になる。未改造版の通常ループにはschedule(runtime)がないため、この既定値は適用されない。

## 評価

融合前に対しては全10条件で平均5.1〜32.9%改善した。未改造版に対しては設定を明示した8条件で平均が上回ったが、P4E4_dynamicの区間は0をまたいでおり、優位を確定する材料としては弱い。P4E4_staticでは22.8%改善し、融合の効果も24.4%と大きい。

既定8スレッドは未改造版より20.8%遅かった。融合だけの問題と解釈せず、dynamic,1という細かい仕事分配とoutput設定を含む差として扱う必要がある。現在版は設定を明示して使うのがよい。P2E8_dynamicとP4E4_staticは次の比較の候補になるが、全条件間の最適性をこの短い測定だけで断定しない。

今回測定したのは現在のOpenMP版であり、pthread常駐版との優劣や、QKV単独・FFN単独の寄与、両者の相乗効果を分離する実験ではない。現在版対融合前の差はQKV+FFN融合の合算効果である。未改造版との差には以前からのschedule/output変更も含む。

## 電源・測定の限界

主測定は全試行の前後でAC=0（バッテリー）、platform_profile=performance、turbo有効だった。電源設定の変更は行っていない。これだけで電力制限がないとは断定しない。

推論測定中の全thermal throttleカウンタは一定だった。全体のafter.jsonでは増加しているが、これは最後の推論試行後、Pythonの集計・bootstrap中の増加だった。measurement_end.jsonに最後の試行の終了状態を抜粋した。カウンタ増加のある3版の組を除く事後感度分析も保存したが、該当は0組で結果は変わらない。

一方、反復ごとの全条件を合わせた平均ms/tokenは約1.60〜2.51と大きく変動した。条件内で3版を隣接実行し、反復を対応させて比較したものの、絶対速度と区間はこの機体・バッテリー状態・短い生成条件での探索的な結果である。長時間のAC固定測定や他モデルへの一般化は別途必要。

最初の予備測定は途中でACが1→0に変わったため主比較から除外した。生ログは理由付きで残しており、上表には含めていない。

## 再実行・検証・保存場所

`python3 src/cpuprofiler/benchmark_compare.py` でビルドから集計まで実行する。既存のBenchmarkConfigを使用し、CPU・人数・scheduleはmain()内のcasesで設定できる。shellのexportは不要で、継承したOMP_*等は除去してから各条件を適用する。参照版は固定コミット、現在版は実行時の作業ツリーを保存する。

既存の融合テストをserialおよび `CC=gcc TEST_OPENMP=1` で実行し成功。MHA/GQA、O2/Ofast、OpenMP 1/4/14スレッドと複数scheduleでlogits・hb2・KV cacheを比較した。今回run.cの変更はしていない。
