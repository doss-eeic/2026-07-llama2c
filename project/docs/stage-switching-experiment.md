# 演算ステージ別CPU構成：初回実験の要件案

作成日：2026-10-19。性能改善率などの閾値は実験前に置く暫定基準。

## 目的と仮説

stories15MのFP32・batch=1・逐次推論で、Transformer内部をPコアのみ、
Output GEMVだけをP+Eコアで処理すると、固定CPU構成よりforward時間が短くなるか検証する。
Output単体の高速化と、切替・同期を含む全体の高速化を別々に判定する。

既存メモのP4_HTはLayers 0.8324 ms、Final 0.7925 ms、Forward 1.6276 ms。
これは過去の参考値であり、今回の比較基準には同一実行環境で再計測した値を使う。
FinalはRMSNormとWclsを含むため、0.7925 msをWcls単体の値として扱わない。

## 初回の範囲

- 対象機は既存実験のIntelハイブリッドCPUを搭載したLinux環境。
  現在のMac上で同じP/E構成の性能結論は出さない。
- P4_HTは2物理Pコアの4論理CPU、E2は通常Eコア2個という実験上の名称。
  CPU IDを決め打ちせず、物理コア・SMT・L2共有・利用可能CPUを実機で確認する。
  通常EとLP Eは分け、初回はLP Eを含めない。判別不能なCPUは手動確認する。
- モデル、tokenizer、コンパイラ、最適化フラグ、OpenMPランタイムは全条件共通。
- 変更対象はCPU参加構成と出力行の分配。内積順序・SIMD・量子化は変更しない。
- 初回はOpenMPで実装。pthread固定プール、llama.cpp移植、自動最適構成探索は次段階。

## 機能要件

1. 元のforwardを参照実装として比較できるようにする。
   現在のrun.cには、添付資料にある関数分割・計測コードはまだ入っていない。
2. GEMV呼び出しにQKV / Attention Output / FFN Up / FFN Gate /
   FFN Down / Outputの種別を付ける。Attention本体は別種の処理として計測する。
   Q/K/Vは初回は集約可。寸法はConfigから取得し、32000×288を実装に固定しない。
3. Transformer側とOutput側のスレッド数、CPU集合、Outputのstatic/dynamic、
   チャンク行数を実行時に指定できるようにする。
4. Transformer側の全OpenMP領域に方針を適用する。
   matmulだけでなくcompute_attentionの並列領域も対象にする。
   Final RMSNormはメインスレッドで実行し、混在参加はWclsのGEMVだけに限定する。
5. 各ワーカーの許可CPU集合と実行CPUを、4人・6人それぞれのチームで記録する。
   メインスレッドもP側に固定し、想定配置を満たさない試行は無効扱いにする。
   スレッド数の指定やtasksetだけでは配置の成立とみなさない。
6. 時間計測区間内にfprintfしない。値はバッファに保存し、測定後にまとめて出力する。
   詳細計測のON/OFFを設け、主比較は詳細計測OFFでも行う。
7. 数値比較・配置検証・速度測定を分ける。重い検証処理を速度測定に混ぜない。

## 実験1：計測・配置・正しさの確認

- 同じビルド設定で参照版と変更版を比較し、同じ入力トークン列に対するlogitsを確認する。
- 出力行だけの分割変更ではビット一致を第一目標とする。
  不一致があればNaN/Inf、最大絶対誤差、相対誤差を記録して原因を調べる。
  許容誤差で判定する場合は、速度結果を見る前に基準を決める。
- Greedy生成のトークンID列と実際のforward回数も一致を確認する。
- 構成ごとに、各スレッドの配置と実際の参加人数を確認する。

## 実験2：Output単体の成立確認

最初はP4_HT、P4_HT+E2の2構成。E2はL2クラスタへの配置も記録し、
まず固定した1組を使用する。有望なら同一クラスタの2個とクラスタを跨ぐ1+1を比較する。

| CPU構成 | 分配 | チャンク行数 |
|---|---|---|
| P4_HT | static均等 | OpenMPの均等分割 |
| P4_HT | dynamic | 32 / 64 / 128 |
| P4_HT+E2 | static均等 | OpenMPの均等分割 |
| P4_HT+E2 | dynamic | 32 / 64 / 128 |

同じWclsと入力ベクトルで繰り返し、出力を検証・利用して計算の消去を防ぐ。
並列領域の開始から完了までを測り、起床・分配・同期の費用を含める。
単体反復のキャッシュ状態は推論全体と異なるため、単体結果だけで採用しない。

ここで選んだチャンクは探索結果とし、別の全体測定で評価する。
初回からstatic weightedやP/E別チャンクを組み合わせず、共通dynamicの効果を先に確認する。

## 実験3：推論全体での比較

| 条件 | Transformer | Output | 目的 |
|---|---|---|---|
| B0 | P4_HT・static | P4_HT・static | 従来相当の基準 |
| B1 | P4_HT・static | P4_HT・dynamic | 分配変更だけの効果 |
| B2 | P4_HT+E2・static | P4_HT+E2・dynamic | 全体混在の対照 |
| B3 | P4_HT・static | P4_HT+E2・dynamic | ステージ切替の効果 |

B1〜B3は同じOutputチャンク行数を使用する。
B3対B1でE追加、B3対B2でTransformerへのE参加を除く効果を評価する。
同じソース・バイナリの実行時設定で切り替える。

## 測定要件

- 主指標：forward入口からlogits完成までの経過時間。同期、チーム変更、待機を含む。
- 副指標：Transformer時間、Final RMSNorm時間、Output GEMV時間、生成tokens/s。
  詳細ステージ時間の合計をforward経過時間と呼ばない。
- 速度比較は固定トークン列の再生で同じ位置・同じ回数のforwardを実行する。
  例：事前に固定した256トークン。seq_lenを超えない長さを使用する。
  別途、既存のprompt / seed=42 / temperature=0の生成で動作確認する。
  EOSで早期終了した生成を256回測定として扱わない。
- 各条件で測定外のウォームアップを行う。
  初回トークンのロード等を除く定常状態の集計と、全トークンの集計を分け、
  除外範囲は全条件で固定する。
- 初回は各条件10試行。1ブロックで全条件を実行し、順序をseed付きでランダム化する。
  1試行内の多数のトークンを、独立した多数の試行として扱わない。
- 試行ごとの平均ms/tokenを主に比較し、試行間の中央値とMAD、
  トークン時間のp95、ブロック対応の改善率を併記する。
- AC電源・電源設定・バックグラウンド負荷を揃える。
  CPU、カーネル、トポロジー、OpenMP環境変数、wait policy、
  コンパイラ・フラグ、git revisionと差分、モデルとtokenizerのハッシュを保存する。
  温度・周波数も取得可能なら保存する。
- OpenMP無効のビルドは検出して停止する。perf等の追加診断は別の試行で行う。

## 判定と次の段階

実装の成立条件は、正しい出力、指定どおりの配置、全条件の比較データが揃うこと。
高速化できなかった場合も検証結果として成立する。

暫定的な採用基準は、B3のforward時間がB0とB1の両方より中央値で5%以上短く、
それぞれに対して10ブロック中8ブロック以上で高速、出力一致、p95の悪化が5%以内。
この閾値は統計的有意性の証明ではなく、次の実装に進むための実用上の基準。
別セッションで再測定してから恒常的な改善と判断する。

- B2が最速：全体混在の方針を優先する。
- B3が最速：演算別参加構成に価値がある。固定ワーカープールで再評価する。
- Output単体だけ改善：全体で得られる削減量と起床・同期の費用を比較する。
  差が小さいなら実装を複雑化せず、明確な費用がある場合に固定プールを試す。
- B0/B1が最速：E追加を採用せず、E数やL2配置を調べるかを結果から決める。
- 差がばらつきの範囲：優劣保留。条件を増やす前に配置・熱・待機設定を点検する。

次段階ではP4_HT+E4、P2（SMTなし）、Eのみの有力構成、static weighted、
P/E別チャンクを必要に応じて比較する。
llama.cppへの移植時は、その時点の実装とカーネルを確認して別途検証する。
