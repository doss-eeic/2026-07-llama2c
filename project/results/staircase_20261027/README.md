# 高速化の段階ごとの速さ（2026-10-27）

発表用に、元のコードから最速構成までの各段階を、同じ PC・同じ回の中で測り直した。
16通りの設定を1ブロックとし、ブロックごとに順番をランダムに入れ替えて25ブロック測った。
これまでの資料の数字は日やセッションが違うので、発表ではこの測定の数字にそろえる。

## 結論

元のコード 633 tok/s から、12スレッド 0–11 の 1601 tok/s まで、2.53倍速くなった。全400回で生成文は同一だった。

| 段階 | 内容 | 中央値 tok/s | 1つ前からの伸び [95%区間] | 元のコードの何倍か |
|---|---|---:|---:|---:|
| S1 | 元のコード、P コア 0–3 の4スレッド | 633 | — | 1.00 |
| S2 | ＋hugepage | 666 | +5.1% [4.8, 5.4] | 1.05 |
| S3 | ＋QKV と W1/W3 の行列をまとめる | 706 | +6.1% [5.8, 6.3] | 1.12 |
| S4 | ＋int8 による二段階の厳密な argmax | 948 | +34.5% [33.8, 35.1] | 1.50 |
| S5 | ＋OMP_WAIT_POLICY=ACTIVE | 1052 | +11.4% [10.0, 11.6] | 1.66 |
| S6 | 9コア 0,2,4–10、guided,4（班の設定） | 1567 | +48.9% [47.9, 50.0] | 2.48 |
| S7 | kasikoi2 が選んだ設定 | 1556 | −0.7% [−1.4, 0.0] | 2.46 |
| S8 | 12スレッド 0–11、static | 1601 | +2.9% [2.2, 2.9] | 2.53 |

1つ前からの伸びは、同じブロックの中での比の中央値。S7 以外は25ブロック中23〜25ブロックで速くなった。

S7 は、kasikoi2_quiet_20261026 の1回目の探索が選んだ設定（9コア、guided,16、ACTIVE、GOMP_SPINCOUNT=10000、g144）。探索そのものは今回は実行していない。

## 工夫ごとの効果の切り分け

| 比べたもの | 比 [95%区間] | 前者が速かったブロック |
|---|---:|---:|
| 行列をまとめるだけ（hugepage なし） ÷ 元のコード | 1.061 [1.055, 1.064] | 25/25 |
| hugepage だけ ÷ 元のコード | 1.051 [1.048, 1.054] | 25/25 |
| 行列をまとめた上に hugepage を足す | 1.051 [1.051, 1.054] | 25/25 |
| 櫻田の `-w 5` ÷ master の `-w 1` | 0.994 [0.990, 0.997] | 1/25 |
| 櫻田の `-w 5 -a 1` ÷ master の `-w 1 -a 1` | 0.979 [0.971, 0.987] | 1/25 |
| 9コア：ACTIVE あり ÷ なし（guided,4） | 1.264 [1.255, 1.275] | 25/25 |
| 9コア：guided,4 ÷ static（ACTIVE） | 1.079 [1.077, 1.093] | 25/25 |
| 12スレッド：static ÷ guided,4（ACTIVE） | 1.014 [1.014, 1.022] | 21/25 |
| 9コア guided,4 ÷ 12スレッド guided,4（班の比較と同じ設定） | 1.000 [0.986, 1.000] | 7/25 |
| kasikoi2 の結果 ÷ その出発点（全14CPU、既定設定） | 1.620 [1.613, 1.631] | 25/25 |
| 元のコード：0–11 ÷ 0–3 | 1.156 [1.152, 1.167] | 25/25 |
| 0–11 で比べた、S8 ÷ 元のコード | 2.188 [2.168, 2.197] | 25/25 |

読み取れること:

- 行列をまとめる効果と hugepage の効果は打ち消し合わず、掛け算になる。1.061 × 1.051 ≈ 1.115 で、S3 の1.12倍と一致する。
- 元のコードは CPU を3倍にしても1.16倍にしかならない。工夫後は、4スレッドの948 tok/s から12スレッドの1601 tok/s まで伸びる。
- 9コアのように P と E が混ざると guided が必要になる。12スレッドは static でよい。
- 静かな PC では、班と同じ guided,4 で比べた9コアと12スレッドは互角だった。
- 櫻田の実装と master の実装はほぼ同じ速さで、argmax まで入れると master のほうがわずかに速い。発表では master の数字を使う。

## これまでの資料の数字との対応

| これまでの資料 | この測定 |
|---|---|
| 元のコード 635 → hugepage 662 → まとめる 700 → argmax 915 tok/s（Google ドキュメント Day6、櫻田の実装） | 633 → 666 → 706 → 948 tok/s（argmax は master の実装） |
| hugepage +4.5%、まとめる +5.8%、argmax +31.7% | +5.1%、+6.1%、+34.5% |
| 3つの工夫の合計 1.44倍 | 1.50倍 |
| kasikoi2 の結果 1567 / 1575 tok/s | 1556 tok/s |
| 9コア guided,4 1552〜1567 tok/s | 1567 tok/s |
| 12スレッド 1601 / 1619 tok/s | 1601 tok/s |

argmax 後の伸びが Day6 より大きいのは、master の実装で測ったため。櫻田の実装で測った値（F_ours_w5a1）は 929 tok/s で、Day6 の 915 tok/s に近い。

## ファイル

`session/` は、学科PC で出力された結果ディレクトリそのもの（tar.gz は除く）。

- `runs.jsonl`：全400回の記録。設定、コマンド、OpenMP の環境変数、tok/s、生成文の sha256、他の処理に CPU を取られた回数、他のプロセスが使った CPU 秒、前後の温度、周波数、時刻。
- `warmup.jsonl`：測定前のウォームアップ16回の記録。
- `staircase.csv`：S1〜S8 の中央値、平均、1つ前からの伸びとその95%区間、元のコードに対する倍率。グラフ作成用。
- `summary.txt`、`analyze_staircase.py`：集計結果と集計スクリプト。
- `blocks.tsv`：ブロックごとの待ち時間と温度。
- `quiet_check.txt`：他のプロセスの CPU 使用量。
- `environment.txt`：OS、電源、ソースとバイナリの sha256、候補一覧、CPU 構成。
- `runone.py`：1回の実行と記録を行うスクリプト。
- `staircase_check.sh`：実行したスクリプトのコピー。dev/sakurada 27acb8d1 のファイルと一致する。
- `errors.log`：空（エラーなし）。

`SHA256SUMS` はこのディレクトリの全ファイルのハッシュ。

## 再現方法

集計だけをやり直す場合は、リポジトリのルートで次を実行する。`staircase.csv` は完全に一致し、`summary.txt` も最終行に出るディレクトリのパス以外は一致することを確認済み。
`staircase.csv` は指定したディレクトリに上書きで書き出される。

```sh
python3 project/results/staircase_20261027/session/analyze_staircase.py project/results/staircase_20261027/session
```

測定をやり直す場合は、学科PC のネイティブ Ubuntu で、AC 接続のまま、他のプログラムをすべて閉じてから実行する。所要時間は約10分。

```sh
curl -fsSL https://raw.githubusercontent.com/doss-eeic/2026-07-llama2c/27acb8d1/staircase_check.sh -o staircase_check.sh && bash staircase_check.sh
```

## 注意点

- 中央値で比べている。元のコードで1回だけ 455 tok/s に落ちた回があり、平均はその分だけ下がる。
- 1つのブロックの中では休まずに続けて測るので、後ろの順番ほど温度が高い。順番を毎回入れ替えているので、影響はどの設定にも均等にかかる。
- 熱による速度制限のカウンタは、このカーネルでは読めない可能性があるので記録していない。
- 測定は1台の PC で1回だけ。別の日や別の PC では、絶対値が数%変わることがある。
