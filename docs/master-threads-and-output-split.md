# master のスレッド数と、移行後の output 分配

測定・整理日: 2026-10-26。Core Ultra 5 225U / stories15M / greedy / `Once upon a time` / `-n 256` / seed 42。

**master では9コア（0,2,4–10）が最速だった。12スレッドにすると約9〜11%遅い。
融合・二段階argmax を揃えた版に output 分配を移しても、分配OFFより少し遅く、改善は確認できなかった。**

## 1. master のスレッド数: 9 vs 12

master `256b0b24` を `gcc 13.3 -Ofast -fopenmp -march=native` でビルド。
共通設定は `OMP_WAIT_POLICY=ACTIVE` / `OMP_SCHEDULE=guided,4` / `OMP_PROC_BIND=close` /
`OMP_DYNAMIC=FALSE` / `-w 1 -a 1 -g 288`。`OMP_PLACES` は CPU 集合をこの順で1つずつ並べ、`taskset` も同じ集合。
2構成を毎巡シャッフルして交互に実行し、warmup 各1回の後30巡。
差は巡ごとの比の平均で、95%区間は巡を単位とする paired bootstrap（10000回）。

|比較|9コア tok/s|12スレッド tok/s|差|95%区間|12が速かった巡|
|---|---:|---:|---:|---:|---:|
|12 = 0,2,4–13（物理12コア、LP-E含む）|1560.9 ± 29.7|1395.5 ± 35.3|−10.57%|−11.49〜−9.65%|0/30|
|12 = 0–11（Pコアの SMT 1,3 を含む）|1552.4 ± 34.9|1407.8 ± 95.4|−9.22%|−11.75〜−6.73%|2/30|

9コア = `0,2,4,5,6,7,8,9,10`（P×2 + E×7）。生成文は全120回で同一。
2つの比較は別の実行で、表の行どうしの絶対値は直接比べない。

遅くなる原因は測っていない。
0,2,4–13 は最大2.4GHz の LP-E（12,13）を含むため、遅いコアに同期が引きずられる可能性がある。
0–11 は SMT の相手どうしが計算資源を取り合う可能性があり、ばらつきも約3倍だった。

## 2. 移行後の output 分配（dev/omp-tmp）

`dev/omp-tmp` で master の QKV/FFN 融合・hugepage・二段階argmax を取り込み、
二段階argmax の全語彙 int8 スコア計算に output だけの人数指定と P/E 重み付き行分配を追加した。
同条件（`-w 1 -a 1 -g 144`、CPU 順・人数・schedule・spin を一致）で各20回の追加確認:

|比較|分配OFFとの差|95%区間|
|---|---:|---:|
|10→10、人数を明示するだけ|+0.84%|−0.56〜+2.25%|
|10→10、均等な手動分配|約−1.8%|—|
|10→10、P側2倍の重み付き|−1.71%|−3.07〜−0.28%|
|9→10、人数変更のみ|−3.84%|−4.95〜−2.67%|
|9→10、P側2倍の重み付き|−4.84%|−6.30〜−3.40%|

移植した版の分配OFFは未変更 master と差がなかった（−0.14%、区間 −0.95〜+0.75%）。
以前の「FP32版989 対 master 1575」の差は最適化の有無の違いで、分配のコストではなかった。

遅くなる理由は推測で、次のように考えている。

- 二段階argmax の int8 スコア計算は FP32 output より軽く、P/E の速度差を固定比率で埋める利点が小さい。
- `guided` は遅いコアの分を実行時に吸収するため、固定比率の分配が上回れない。
- P:E=2:1 は FP32 版で効いた比率で、重みは1・2・3しか試していない。

1.2〜1.5 のような細かい重みや P 数の組み合わせは未探索。

詳細・生データ・再現手順は `dev/omp-tmp` の `b6ee9e86`、`docs/optimized-output-benchmark.md` と
`results/optimized_output_*_20261026/` にある。

## 結論

現状は master の非分離・9コア構成（SMT と LP-E を使わない）を推奨する。
output 分配と人数切替は、今回の候補では速くならなかった。
